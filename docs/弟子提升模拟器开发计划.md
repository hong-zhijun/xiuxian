# 弟子提升模拟器开发计划

弟子详情里新增「提升模拟」：玩家可以随意调这名弟子的**境界**、**三件装备**（品质、主副属性、祭炼重数）和**悟道值分配**，
实时看到攻防身等属性与战力的变化、每一项单独能加多少战力，以及要花多少代价，
用来判断「这名弟子是换装备提升大，还是修炼升境界提升大」。

**模拟不改任何数据**：不调用任何写接口，关掉弹窗就丢弃。

金额一律是**最小单位**（1 展示单位 = 1000 最小单位），展示用 `apps/web/src/utils/format.ts` 的 `formatAmount`。

---

## 1. 产品规则（已和产品确认，不要改）

- 入口：弟子详情（`DiscipleDetailDialog.vue`）战力标签旁边加一个小按钮「提升模拟」，点开弹窗（用 `ModalShell`）。
- 不做演武场选项（只算弟子本身的战力）。
- 装备副属性由玩家自己选（属性 + 数值，数值限制在该品质的副属性范围内）。
- 要显示代价（见 2.4）。
- 战意天赋加成由**服务端多下发一个数值字段**（见 3.1），前端不抄表。

## 2. 规则细节

### 2.1 可调项

1. **境界**：一个下拉框，列出从「当前境界层数」起往上的所有层（数据来自 `state.realmCatalog`，按境界顺序展开 `stages`）；默认 = 当前。
2. **装备三格**（兵器 / 护甲 / 法器；装备视图未解锁或没加载时整块显示「炼器未开放」并禁用）。每格一个模式：
   - **保持当前**（默认）：身上穿着的那件；可以把祭炼重数往上调（当前重数 ~ 12），不能往下调。没穿装备时这个模式就是「空着」。
   - **空着**：卸下。
   - **自定义一件**：选品质（凡 / 灵 / 宝 / 仙）、主属性（兵器固定攻击、护甲固定防御、法器可选身法 / 幸运）、
     副属性（攻击 / 防御 / 身法 / 幸运 / 体魄中不同于主属性的一项）、副属性数值（该品质 `subMin ~ subMax` 的整数，默认取中间值向下取整）、
     祭炼重数（0 ~ 12，默认 0）。
3. **悟道值**：攻击 / 防御 / 身法三个数字输入（每项 ≥ 0），三项之和 ≤ `daoInsightRemaining`（还能累计分配的额度），
   且每项加完后**基础属性**不超过 100。默认全 0。旁边提示「手上有 N 点」，超出手上的部分在代价里写「还需 X 点悟道值（赌坊 / 悟道丹）」。

右上角一个「还原」按钮：所有可调项回到默认。

### 2.2 装备数值

一件装备对弟子的贡献 = 主属性 + 副属性 + 战力加成（基点）：

- **自定义一件**（品质 q、祭炼 r 重）：
  - 主属性 = q.mainValue + Σ(第 1..r 重的 `mainGain`)
  - 副属性 = 玩家选的数值 + Σ(第 1..r 重的 `subGain`)
  - 战力加成 = q.powerBonusBp + Σ(第 1..r 重的 `powerBonusGainBp`)
  - `mainGain / subGain / powerBonusGainBp` 取装备视图 `refineGuide.qualities[q].rows`（每行是「冲到这一重」的增量）。
- **保持当前**（当前 c 重 → 调到 r 重，r ≥ c）：在这件装备现有的 `mainValue / subValue / powerBonusBp` 上，
  加 Σ(第 c+1..r 重的增量)。
- 弟子模拟后的装备加成 = `disciple.gear` − 身上这一格旧装备的贡献 + 这一格新装备的贡献（三格分别算）；
  战力加成同理：`disciple.gearPowerBonusBp` − 旧 + 新。

> 身上穿的装备从装备视图 `items` 里按 `discipleId === 弟子 id && slot === 格子` 找。

### 2.3 战力公式（与服务端 `realms.ts discipleCombatPower` 一模一样，含取整）

```
base   = (境界序号 × 3 + 层数) × 10                         // 境界序号 = realmCatalog 下标，层数 1~3
attr   = (攻 × 0.4 + 防 × 0.35 + 身 × 0.25) / 100            // 攻防身 = 基础 + 悟道值 + 装备
power  = floor(base × (1 + attr) × (1 + 装备战力加成 / 10000))
战意   = 天赋是战意时，目标境界的加成 bp（3.1 新字段）；>0 时 power = floor(power × (10000 + bp) / 10000)
```

**验收硬条件**：所有可调项都是默认值时，算出来的战力必须等于 `disciple.combatPower`（测试里要覆盖：无装备、有装备、战意天赋）。

### 2.4 代价

- **升境界**（当前 → 目标）：
  - 修为：当前层还差 `requiredCultivation − cultivation`（`cultivation` 用弟子详情已有的实时修为 `liveCultivation ?? disciple.cultivation`），
    加上中间每一层的 `requiredCultivation`（目标层自己的不算）。突破成功后修为清零（服务端 `service.ts` 突破成功 `cultivation = 0`）。
  - 灵气：每次突破的 `breakthroughCost` 相加（从当前层到目标层的前一层）。
  - 预计时间：修为 ÷ `disciple.cultivationRatePerHour`（`formatHours` 口径：不到 1 小时 / 约 N 小时 / 48 小时起按天），文案注明「按当前修炼速度，不含突破失败」。
- **装备**：
  - 自定义一件：炼器消耗（装备视图 `forgeOptions` 里该品质的 `cost`，并注明成功率 `odds.success`；该品质 `unlocked = false` 时写「炼器坊等级不够」）
    + 祭炼第 1..r 重的 `cost` 之和。
  - 保持当前并调高祭炼：第 c+1..r 重的 `cost` 之和。
  - 空着：无。
- **悟道值**：超出手上的点数写「还需 X 点悟道值」，否则「无」。
- 所有资源按 resourceId 合并后显示（如「1200 灵石 + 300 矿石 + 4 玄铁」，资源名从 `state.resources` 取）。

### 2.5 展示

1. **总对比**：两列「当前 / 模拟」：境界、攻击、防御、身法、幸运、体魄（装备加成用括号显示，与详情页一致）、战力，
   战力后面写增幅（`+12%`，不足 10% 保留一位小数；负数也显示）。
2. **单项拆解**（核心）：每一项改动**单独**作用在当前状态上的战力增幅与代价，一行一项：
   - 境界（目标 ≠ 当前时）、兵器、护甲、法器（该格不是「保持当前且重数没变」时）、悟道值（有分配时）。
   - 按增幅从高到低排；增幅最高的一行标「提升最大」。
   - 最后一行「全部一起」：总增幅 + 总代价（注意各项相乘，总增幅 ≠ 各项相加）。
3. 没有任何改动时，拆解区显示「调整上面的选项看看能提升多少」。

## 3. 代码结构

### 3.1 服务端（只加视图字段，不改规则、不动 game-config、不加迁移）

- `apps/server/src/modules/game/talents.ts` 的 `talentCatalog()`：`values` 每项加 `bp: number`（= `talentBonusBp(def.id, realm.id)`），
  `TalentCatalogEntry` 类型同步。前端判断：弟子天赋 id 为 `combat`（战意）时，取 `values.find(v => v.realmId === 目标境界).bp`；其他天赋按 0。
  （服务端 `discipleCombatPower` 用的是 `talentBonusBp(talent, realmId, 'combat')`，只有战意生效，口径一致。）
- `apps/server/src/modules/game/view.ts` 的 `refineGuideView()`：`qualities` 每项加 `mainValue`、`subMin`、`subMax`、`powerBonusBp`
  （取 `equipment.ts` 的 `EQUIPMENT_QUALITIES`），`RefineGuideView` 类型同步。
- 测试：`tests/game/talent-rules.test.ts` 补一条 `bp` 与 `talentBonusBp` 一致；补一条 `refineGuideView()` 新字段与品质表一致（放在现有装备 / 祭炼测试文件里，找 `refineGuideView` 或品质表相关测试）。

### 3.2 前端

- `apps/web/src/api/game.ts`：`TalentCatalogEntry.values[].bp`、`RefineGuideView.qualities[].mainValue / subMin / subMax / powerBonusBp`。
- `apps/web/src/utils/upgradeSimulator.ts`（新，纯函数，不碰 Vue / DOM，写法照 `utils/advisor.ts`）：
  - 输入：弟子（只声明用到的字段）、`realmCatalog`、`talents`、装备视图（可为 null）、`resources`（取名字）、当前修为、模拟选项。
  - 模拟选项类型：`{ target: { realmId, stage }, slots: Record<'weapon'|'armor'|'artifact', SlotPlan>, insight: { attack, defense, speed } }`，
    `SlotPlan = { mode: 'keep', refineLevel } | { mode: 'empty' } | { mode: 'custom', quality, mainAttr, subAttr, subValue, refineLevel }`。
  - 导出：`defaultPlan(...)`、`simulate(...)` → `{ current: Snapshot, simulated: Snapshot, breakdown: Row[], total: Row }`，
    `Snapshot = { realmName, stageName, attrs（基础 + 装备两部分）, combatPower }`，`Row = { id, label, gainRatio, cost: Record<string, number>, notes: string[], best: boolean }`。
  - 校验函数：悟道值是否超额度 / 超 100、副属性数值是否在范围内等，返回错误文案（UI 显示在对应输入旁，并且不参与计算——非法时按 0 / 夹到范围内）。
- `apps/web/src/components/UpgradeSimulatorDialog.vue`（新）：只渲染与收集输入，不写规则；手机 360px 宽不横向溢出（选项竖排）。
- `apps/web/src/components/DiscipleDetailDialog.vue`：战力标签旁加按钮，打开模拟弹窗，传 `state`、`disciple`、`equipment`、`liveCultivation`。
- `apps/web/src/data/changelog.ts`：最前面加一条（id `2026-10-14-upgrade-simulator`）。

## 4. 测试

`tests/web/upgrade-simulator.test.ts`（造数据方式照 `tests/web/advisor.test.ts`）：

- 默认选项下战力 == 服务端公式结果：无装备、三件装备（含祭炼）、战意天赋（取 bp）三种情况；用服务端 `discipleCombatPower`（`apps/server/src/modules/game/realms.ts`）对照算期望值。
- 升境界：战力与修为 / 灵气 / 时间代价正确（跨境界、同境界跨层）；战意天赋按目标境界的 bp。
- 自定义装备：主 / 副属性、战力加成含祭炼累计；替换身上的装备时扣掉旧装备贡献；空着时扣掉。
- 保持当前调高祭炼：只加 c+1..r 的增量与代价。
- 悟道值：加到属性；超手上点数时代价里写还需多少；超额度 / 超 100 的校验文案。
- 单项拆解：每项单独算、按增幅排序、最大的一项 best；「全部一起」是组合结果。
- 装备视图为 null：装备格不参与，不报错。
