# V6 秘境探索重构 — 开发计划

## 一、背景

当前秘境是一次性判定：选人 → 扣资源 → 随机成功/失败 → 发奖。玩法单薄。
重构目标：保留原有速通模式，新增**多关卡交互探索**，由 OpenRouter Decisions API 做结构化判定。

## 二、核心规则

| 项目 | 说明 |
|------|------|
| 探索模式 | 点「探索」进入多关卡交互流程；点「速通」走旧逻辑（一次判定） |
| 关卡数 | 低级秘境（宗门 1-3 级可进）3 关，高级秘境（宗门 4+ 级可进）5 关 |
| 每关流程 | 服务端从遭遇池随机抽一个场景 → 前端展示场景描述 + 2~3 个选项 → 玩家选择 → 后端调 Decisions API 判定 → 返回结果 |
| 失败处理 | 判定失败 → 探索立即结束，**已获奖励保留**，弟子可能受伤 |
| 通关奖励 | 全部关卡通过后额外发一笔通关奖励（在各关卡累计奖励之上） |
| 入场费 | 开始探索时一次性扣除（与速通相同） |
| 每日限次 | 速通和探索共享同一个每日限次计数 |
| 出战人数 | 与原秘境定义一致（minParty ~ maxParty） |

## 三、OpenRouter Decisions API 客户端（解耦模块）

### 3.1 新文件 `apps/server/src/infra/openrouter/decisions.ts`

```ts
/**
 * OpenRouter Decisions API 通用客户端。
 * 解耦设计：不依赖任何游戏业务逻辑，可被秘境、破境、事件等任意系统复用。
 */

/** noul 题型：返回 0~1 概率 */
interface NoulQuestion {
  type: 'noul';
  instructions: string;
  criteria: { true: string; false: string };
}

/** choice 题型：返回选中项 + 各项概率分布 */
interface ChoiceQuestion {
  type: 'choice';
  instructions: string;
  criteria: Record<string, string>;
}

/** score 题型：返回 0~1 分数 */
interface ScoreQuestion {
  type: 'score';
  instructions: string;
  criteria: string[];  // 从低到高的锚点描述
}

type Question = NoulQuestion | ChoiceQuestion | ScoreQuestion;

interface DecisionsRequest {
  model: string;
  state: string;
  questions: Record<string, Question>;
}

interface NoulAnswer { noul: number }
interface ChoiceAnswer { choice: string; probabilities: Record<string, number> }
interface ScoreAnswer { score: number }

type Answer = NoulAnswer | ChoiceAnswer | ScoreAnswer;

interface DecisionsResponse {
  answers: Record<string, Answer>;
}

const DECISIONS_URL = 'https://openrouter.ai/api/alpha/decisions';
const DEFAULT_MODEL = '~typesafe/jev-latest';

/**
 * 调用 OpenRouter Decisions API。
 * @param apiKey - OPENROUTER_API_KEY（从 Worker secret 注入）
 * @param state  - 给模型的上下文描述（纯文本）
 * @param questions - 要让模型回答的结构化问题
 * @param model  - 决策模型 id，默认 ~typesafe/jev-latest
 */
export async function decide(
  apiKey: string,
  state: string,
  questions: Record<string, Question>,
  model: string = DEFAULT_MODEL,
): Promise<Record<string, Answer>> {
  const res = await fetch(DECISIONS_URL, {
    method: 'POST',
    headers: {
      'Authorization': `Bearer ${apiKey}`,
      'Content-Type': 'application/json',
    },
    body: JSON.stringify({ model, state, questions } satisfies DecisionsRequest),
  });
  if (!res.ok) {
    const text = await res.text().catch(() => '');
    throw new Error(`Decisions API ${res.status}: ${text}`);
  }
  const data = (await res.json()) as DecisionsResponse;
  return data.answers;
}
```

**要点：**
- `decide()` 是唯一的导出函数，参数全部显式传入，不读全局状态
- 游戏侧调用时自行从 `env.OPENROUTER_API_KEY` 取 key
- 后续破境概率、随机事件等场景可直接复用同一个 `decide()`

### 4.2 Decisions API 调用设计

每当玩家选择一个选项后，后端构造如下请求：

```ts
const answers = await decide(env.OPENROUTER_API_KEY, 
  // state：把场景 + 选择 + 弟子实力浓缩为一段文字
  `秘境难度${realm.difficulty}，队伍战力${power}。` +
  `遭遇：${encounter.description} ` +
  `选择：${choice.label}`,
  {
    outcome: {
      type: 'choice',
      instructions: '根据队伍实力与选择的合理性，判断本次遭遇的结果',
      criteria: {
        great_success: '完美通过，额外收获',
        success: '顺利通过',
        failure: '失败，探索终止',
      },
    },
    injury: {
      type: 'noul',
      instructions: '本次遭遇中弟子是否受伤',
      criteria: {
        true: '选择冒险或实力不足导致受伤',
        false: '安全通过或选择了稳妥方案',
      },
    },
  },
);
```

**后端根据 answers 决定：**
- `outcome.choice === 'great_success'` → 通过 + 1.5x 本关奖励
- `outcome.choice === 'success'` → 通过 + 1.0x 本关奖励
- `outcome.choice === 'failure'` → 探索终止，已有奖励保留
- `injury.noul > 0.6` → 随机一名弟子受伤（与旧秘境受伤逻辑一致）

**注意：** 如果 Decisions API 调用失败（网络超时、key 无效等），回退到本地随机判定（与速通同一逻辑），不要让玩家卡住。

## 六、后端 API

### 6.1 新增路由

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/game/realm-explore/active` | 查询当前进行中的探索（恢复断点） |
| POST | `/game/realm-explore/start` | 开始探索：扣入场费 → 建记录 → 抽第 1 关遭遇 → 返回 |
| POST | `/game/realm-explore/choose` | 提交选择：调 Decisions API → 判定 → 推进/终止 → 返回结果 |
| POST | `/game/realm-explore/abandon` | 放弃探索：保留已获奖励，标记 failed |

### 6.2 `/game/realm-explore/start`

请求体：
```ts
{ realmId: string, discipleIds: string[] }
```

逻辑：
1. 结算（与旧 explore 一致）
2. 校验：秘境存在、等级足够、人数合法、无进行中探索、每日限次
3. 扣入场费
4. 算关卡数：`requiredSectLevel <= 3 ? 3 : 5`
5. 从遭遇池中随机抽第 1 关的遭遇
6. 创建 `realm_explorations` 记录（status='in_progress', current_stage=0, current_encounter=抽到的遭遇）
7. 写 `explorations` 表（复用旧表做限次统计，success=0 先占坑，通关后更新为 1）
8. 一次 batch 提交
9. 返回 `{ state, exploration: { id, realmName, totalStages, currentStage, encounter } }`

### 6.3 `/game/realm-explore/choose`

请求体：
```ts
{ explorationId: string, choiceId: string }
```

逻辑：
1. 查 `realm_explorations`，校验 status='in_progress'、choiceId 在当前遭遇的选项中
2. 调 `decide()` 获取判定结果
3. 根据 outcome：
   - **成功/大成功**：累加本关奖励到 `rewards_collected`、current_stage+1
     - 如果 current_stage === total_stages → 追加通关奖励 → status='completed' → 资源入账
     - 否则 → 抽下一关遭遇 → 更新 current_encounter
   - **失败**：status='failed' → 已有 rewards_collected 入账 → 可能弟子受伤
4. injury 判定：`injury.noul > 0.6` 时随机一名弟子受伤
5. 一次 batch 提交（资源入账 + 探索记录更新 + 弟子受伤）
6. 返回 `{ state, result: { outcome, rewards, injury, nextEncounter?, finalRewards? } }`

### 6.4 `/game/realm-explore/active`

返回当前 sect 的 in_progress 探索记录（含 encounter 信息），没有则返回 null。用于页面刷新后恢复。

### 6.5 `/game/realm-explore/abandon`

请求体：
```ts
{ explorationId: string }
```

逻辑：标记 failed → 已有 rewards_collected 入账 → 返回 state。

响应中新增字段 `exploreEnabled: boolean`（读 `env.REALM_EXPLORE_ENABLED`），前端据此决定是否显示「探索」按钮。

## 八、每关奖励算法

以秘境原有的 `rewards` 为基础：

```
每关基础奖励 = 秘境总奖励 / (总关卡数 + 1)
大成功倍率 = 1.5
通关额外奖励 = 秘境总奖励 / (总关卡数 + 1)   // 相当于多一关的奖励
```

例：迷雾森林总奖励 灵石 30000 + 灵药 15000，3 关：
- 每关基础：灵石 7500 + 灵药 3750
- 通关额外：灵石 7500 + 灵药 3750
- 全部通过总计：灵石 30000 + 灵药 15000（与速通成功相同）
- 大成功额外加 50%，所以交互探索有超越速通的收益上限

## 九、Decisions API 降级策略

如果 `decide()` 调用失败（HTTP 错误、超时 > 5 秒、解析失败）：
1. 回退到本地随机判定：用旧的 `explorationSuccessChanceBp()` 算成功率，随机判定
2. 记日志（warn 级别），不影响玩家体验
3. 前端无感知，结果格式完全一致
