# 弟子属性与综合评分开发计划

## 1. 目标与边界

新增幸运、体魄两项有实际作用的属性，并用当前六项属性计算综合评分，让玩家在招贤和名册中直接判断弟子属性好坏。改善今后生成的弟子攻防身法极度割裂的问题。已有弟子的资质、攻防身法、天赋、境界、修为及淬体丹成果一律不重掷、不归一化、不回退。

当前代码：`names.ts` 分别独立生成 1..100 的资质/攻/防/速；初始弟子在 `service.ts` 另用 `randomAptitude()` 独立生成。`DiscipleRow` 和写入语句在 `repository.ts`；私有弟子状态与招贤预览由 `view.ts`/`service.ts` 返回；前端名册、详情、四轴雷达、招贤台分别在 `DiscipleRoster.vue`、`DiscipleDetailDialog.vue`、`DiscipleRadarChart.vue`、`RecruitDialog.vue`。历练的额外收获与受伤在 `journey.ts`/`service.ts` 出发时掷骰并保存结果。

不做岗位推荐、自动派工、先天潜力分、境界加权分、天赋排名、属性洗点、新丹药或新的秘境/战斗规则。不改旧弟子的原有属性，也不改公共游戏配置及其版本/哈希。

## 2. 第一版规则

### 2.1 属性与评分

- 新增 `luck`（幸运）与 `physique`（体魄），均为 1..100 的整数。迁移为旧弟子填入 50；50 是旧历练概率的机制中性点。新弟子须显式生成并写入，不依赖数据库默认值。
- `attributeScore = Math.round((aptitude + attack + defense + speed + luck + physique) * 10 / 6) / 10`，范围 1.0..100.0，显示固定 1 位小数。由服务端按当前属性现算，不新增评分列、不缓存、前端不另算权威值。淬体丹服用后的返回状态和下次 sync 必须一致；任意一项 +1，显示分至少 +0.1。
- 六项等权是当前属性综合评分，不是战力或岗位效率。境界、修为、天赋和战力不纳入评分，仍独立展示；不同天赋不硬排名。评分降序排序，相同时保持招募顺序。暂不做未经分布校准的 S/A/B 档位，也不把平均值称为招募百分位。
- 新字段与评分只进入本宗私有 `SectStateView.disciples`、招贤预览及本人的招募结果。公开宗门、排行榜、战报、探索历史等契约不扩展；战力、资源产量、修炼、突破公式不变。

### 2.2 幸运、体魄的实际作用

仅作用于单人定时历练，不改全局随机事件、秘境和挑战。以下概率单位为基点（10000 = 100%），输入属性须在 1..100，整数运算由服务端统一完成：

- 额外收获概率 `extraChanceBp = 1500 + (luck - 50) * 10`。幸运 1/50/100 分别对应 10.1%/15%/20%；历练保底奖励和触发后额外 +50% 的数量不变。
- 先按现有战力、方向表与受伤下限算出 `baseInjuryChanceBp`；再算 `modified = floor(baseInjuryChanceBp * (10000 - (physique - 50) * 60) / 10000)`，最终 `injuryChanceBp = max(direction.injuryFloorBp, modified)`。体魄 50 完全保持旧概率；1 最多约 +29.4%，100 最多约 -30%。原方向下限仍有效，高体魄在触底时可能无法继续降低概率。不改受伤持续时间或突破失败冷却。
- `journey.ts` 实现可测纯函数；`previewJourney` 与 `startJourney` 共用同一口径，预览显示两项实际概率。`rollJourneyOutcome` 接收额外收获和受伤概率，继续两次独立掷骰且随机源可注入；更新现有调用与测试，不在函数内另取固定 15%。
- 出发时以当时的属性计算并锁定随机结果、受伤概率；到期/领取不重算、不重掷，未到期不泄漏结果。现有 `disciple_journeys.injury_chance_bp` 继续记录最终概率，旧历史不回填。额外概率无需新历史列，因随机结果已在出发时落库。

### 2.3 新弟子生成

初始弟子与招贤候选人共用同一套属性生成函数：前者用 `Math.random`，后者沿用现有 seeded random；预览、刷新、最终招募必须是同一组完整属性和评分。

- 资质、幸运、体魄各独立取两次 `[0,1)` 随机数，`1 + floor(100 * (r1 + r2) / 2)`：中间常见，极值罕见，三项彼此独立。
- 攻、防、身法共用基础值 `15 + floor(random() * 71)`（15..85）；每项再加独立偏移 `floor(random() * 31) - 15`（-15..15），夹取到 1..100。出生时三项最大差距不超过 30，但允许偏科和少量接近 100 的弟子；资质/幸运/体魄不受这个基础值约束。
- 生成器接受可注入随机源；测试 0、接近 1 的边界、固定种子、范围与最大差距。`generateCandidates` 保留宗门/日期/招募次数/刷新序号的种子输入，反复预览一致；不要无意改变性别、姓名、天赋的合法性。
- 新算法上线前已打开的旧招贤预览可能与新服务端候选人不同。预览附带服务端生成的批次标识（至少包含生成规则版本、宗门 ID、日期键、招募次数、刷新序号）；招募请求回传，服务端核对当前批次，不一致则拒绝并提示重新预览，不扣资源/次数。刷新、跨天或跨版本的旧批次均如此；旧客户端缺少标识时也应明确拒绝并提示刷新页面。批次标识不是授权凭据，原有归属、资源与次数校验照旧。同步更新严格请求 schema、前端 API 与调用链。

## 3. 持久化与契约

1. 新增 `migrations/0016_disciple_rating.sql`（0015 后，不修改旧迁移）：分别执行 `ALTER TABLE disciples ADD COLUMN luck INTEGER NOT NULL DEFAULT 50 CHECK (luck BETWEEN 1 AND 100)` 与 `ALTER TABLE disciples ADD COLUMN physique INTEGER NOT NULL DEFAULT 50 CHECK (physique BETWEEN 1 AND 100)`。不对旧攻防速/资质/服药次数执行 UPDATE，不建评分列。旧测试或脚本只插旧字段时应由默认值兼容。
2. 更新 `repository.ts` 的 `DiscipleRow`、`NewDisciple`、全部弟子 SELECT 与 INSERT；更新 `service.ts` 的初始弟子、招贤预览/招募及相关属性映射。盘点所有直接读写弟子的 SQL；守卫、结算与战斗不得意外覆盖新列。
3. 用一个服务端共享纯函数为私有 `DiscipleView` 和招贤 `RecruitCandidate` 计算评分，避免重复公式和取整分歧。同步更新 `view.ts`、`apps/web/src/api/game.ts` 的私有/招贤类型及招募结果；不改公开契约。
4. 历练只改预览/出发的概率通路，继续采用出发快照；旧记录读取和领取无需新列。修改纯函数参数时同步调整历练相关测试与预览字段注释。

## 4. 页面交互

- `RecruitDialog.vue`：候选卡展示六项精确数值和综合评分（1 位小数）；保持现有紧凑布局。提交批次标识，过期错误重新拉预览并让玩家重新确认，不自动选人或扣费。
- `DiscipleRoster.vue`：现有战力旁显示综合评分；在 `utils/discipleFilter.ts` 添加评分高低排序，并列保持招募顺序；不得遮挡状态与备注。
- `DiscipleDetailDialog.vue`：显示“当前属性”评分、幸运/体魄及其实际作用；把 `DiscipleRadarChart.vue` 从四轴扩为六轴，统一 1..100 比例，保留图旁精确值和无障碍描述。战力独立，不作为雷达轴；检查窄屏和长名字。
- 历练预览显示服务端实际 `extraChanceBp`/`injuryChanceBp`，不写死 15%；旧弟子 50/50 的预览与现在相同。前端不复制评分和概率公式作业务裁决。

## 5. 实施与验收

1. 先确认 `git status` 并保护已有改动。先做纯规则和测试，再做迁移/仓储/服务端视图及历练预览/出发，最后接前端和招贤批次核对；不要只画 UI 或只加数据库字段。
2. D1/Worker 测试：迁移后旧弟子的原属性、境界、修为、服药次数原样，新两项为 50；旧式 INSERT 默认仍可用；初始/招贤弟子六属性均在 1..100；同批预览等于招募，跨天/刷新/生成版本变化的旧批次拒绝且不扣资源或次数。
3. 纯规则和接口测试：评分全 1/全 100/小数取整、淬体后重算；新攻防速最大差距 30、随机边界与固定种子；幸运 1/50/100 对应概率；体魄 1/50/100、方向下限；预览与出发保存的概率一致，两次掷骰独立；出发后改属性、归队/重复领取不重抽；50/50 与旧历练基线一致。
4. 前端测试/人工核对：六项、评分、稳定排序、过期预览重试、服丹后评分刷新、六轴雷达图形与精确值一致；桌面和窄屏无重叠。现有战力、修炼、岗位资源、突破、招贤刷新、历练、炼丹回归正常。
5. 执行 `npm run test:unit`、`npm run typecheck`、`npm run build`、`git diff --check`，报告真实结果；能够使用浏览器时核对桌面/窄屏截图。失败先修复，环境阻塞需说明。不要自动提交或推送。

交付报告包含改动文件、迁移、批次标识和概率口径、测试及视口结果、遗留风险。复审重点：旧数据未重掷、旧 50 值机制不变、预览与写入一致、出发结果不重抽、过期批次不误招、评分随当前属性更新。
