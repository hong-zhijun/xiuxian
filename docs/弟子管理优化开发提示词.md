# 弟子管理优化开发提示词

你正在本仓库实现弟子管理优化。请先完整阅读 `docs/弟子管理优化开发计划.md`，将它作为本次开发与验收规格；再阅读现有 `SectScreen.vue`、`AlchemyPanel.vue`、`App.vue`、前端 API 类型，以及后端 `routes.ts`、`schema.ts`、`service.ts`、`repository.ts`、`view.ts`、0011/0012 迁移与相关测试。请直接完成代码和测试，不要只输出方案。

最终体验：列表仅展示头像及修为进度环、修为数字、姓名、私有备注、境界阶段、战力、当前状态与详情入口。支持姓名/备注搜索、境界/岗位/状态组合筛选及排序。详情展示四轴雷达图和精确属性，能编辑备注、改岗位、破境、服用已有丹药、驱逐弟子。炼丹面板保留炼制，移除全局服药入口。

按以下顺序实施，每一阶段自查完整性：

1. 先运行 `git status`，保留工作区已有改动。新增 `0013_disciple_management.sql`，添加 `disciples.note`；更新读取弟子的所有 SQL、服务端私有视图和前端对应类型，保证旧弟子、新招募弟子备注默认为空。
2. 新增 `POST /api/v1/game/set-disciple-note` 与 `POST /api/v1/game/expel-disciple`。请求与返回形状、校验和规则严格按开发计划；沿用登录/CSRF/Origin、安全错误映射、`SectDraft` 先结算再批量写回模式。备注不进入任何公开视图。驱逐与守擂阵容清理在同一原子 batch；历史保留。补提交时的快照守卫及相关并发测试，不能只读后即无条件删除或更新阵容。
3. 精简列表，做组合筛选、排序和无结果态；详情根据 `discipleId` 读取最新 `state`。将岗位、破境、服药迁入详情，复用已有接口和 App 的完整 `state` 更新；做备注保存和驱逐二次确认。雷达图为资质/攻击/防御/身法（1..100），图旁必须有精确数值，天赋/战力另列；移动端布局完整。
4. 补真实 Worker+D1 迁移/接口测试和筛选状态的纯函数测试，覆盖备注校验与私密、跨宗和重复驱逐、结算后删除、阵容清理、历史保留、人数不足 3 人、并发与失败回滚。回归现有破境/服药/招募/守擂/挑战。核对桌面与窄屏；能用浏览器截图时实际检查。

不要偏离以下规则：

- 不新增独立经验系统；进度环显示现有 `cultivation / requiredCultivation`。可破境只认后端 `canBreakthrough`；修为已满但疗伤/灵气不足不可误标，最高阶段单独显示。
- 备注保存 trim，空串可清空，最多 60 个 Unicode 字符，仅一行纯文本。客户端只在自己的 sync 状态中获得备注。
- 驱逐可使本宗人数低于 3，乃至为 0；不返资源/招募次数，不降宗门等级。驱逐守擂成员必须同步清空手动阵容、提示重新布阵；非成员不动阵容。二次确认之前绝不发送驱逐请求，失败后不丢失详情。
- 丹药配方炼制保留，三种服用规则不变；破境、岗位、战力、挑战等由现有服务端规则裁决。不要改公共配置哈希、添加大型依赖、引入新全局状态管理或做无关重构。
- 不要只改页面或只做接口；不要使用假数据代替后端状态。遇到不影响规则的小细节按仓库惯例自行实现。

完成后运行并真实报告 `npm run test:unit`、`npm run typecheck`、`npm run build` 和 `git diff --check`；失败则修复或说明外部阻塞。自查最终 diff 含迁移、服务端、前端和测试，报告改动文件、关键取舍、视口检查与遗留风险。不要自动提交或推送。完成后将代码交给我做质量复审。
