# 宗门挑战优化开发提示词

你正在一个已打开的「修仙宗门挂机文字游戏」代码库中工作。请完整实现宗门挑战优化，不要只给方案，不要只改文案或常量。

首先完整阅读 `docs/宗门挑战优化开发计划.md`，并将它作为本次开发、测试和验收的唯一产品规格。然后阅读现有挑战相关的迁移、后端 service/repository/view/routes、前端 API 类型和挑战组件，尊重项目现有架构和风格后再修改。

必须实现的核心规则：

1. 每个 UTC+8 自然日可主动挑战 3 次。每场真正受理的战斗都消耗次数，包括失败和零奖励胜利；所有前置校验失败都不消耗。
2. 同一攻方当天最多挑战同一宗门 1 次，重复请求要在战斗前拒绝且不扣次数。
3. 胜利奖励按 `守方等级 - 攻方等级` 计算：`<=-3: 0/0`、`-2: 5/50000`、`-1: 8/75000`、`0: 10/100000`、`+1: 13/125000`、`+2: 15/150000`、`>=+3: 20/200000`，每项依次是声望/灵石存储值。失败始终是 0/0，`>=+3` 奖励封顶。
4. `<=-3` 的目标仍可挑战，但 UI 必须明确警告“胜利无奖励，仍消耗 1 次”。
5. 守方有有效的 3 人手动阵容时按原顺序使用；没有有效阵容但有至少 3 名弟子时，从当前弟子中随机、不重复地选 3 名并随机排序。自动守擂可选中受伤弟子。
6. 手动阵容有重复、非本宗弟子、已失效 ID 或格式问题时，应回退到自动守擂，不要用 0 战力占位。守方总弟子少于 3 名时才不可被挑战。
7. 自动阵容必须在开战时固定为快照，战斗和历史使用同一阵容。战斗前只告知“临时自动守擂”，不暴露当场选中的人和顺序。
8. 被动守擂不消耗守方次数，不给守方发奖。保留现有 3v3 顺序对战和战力规则。

实现要求：

- 新增 `migrations/0012_challenge_rewards.sql`，不修改旧迁移。按计划增加宗门挑战日计数、挑战日志快照和同日同目标唯一约束。旧日志必须仍可读。
- 奖励档位使用单一纯函数/定义表，前端直接显示后端返回的预览和实际奖励，不在多处复制奖励分支。
- 随机选人函数不得改写原数组，并应支持测试注入确定性随机源。
- `SectStateView` 返回每日上限、已用和剩余次数。`PublicSectView` 返回相对当前用户的可挑战状态、阻止原因、防守方式、次数、是否已挑战过、等级差和确切奖励预览。
- `ChallengeResultView` 和新历史记录包含双方等级、等级差、奖励档位和守擂方式快照。旧历史的这些字段为 null 时要正常显示，不得编造值。
- 公开宗门面板和挑战对话框要显示剩余次数、等级差、精确胜利奖励、零奖励警告、重复目标状态和手动/自动守擂状态。排行榜文案更新为每日 3 次。
- 次数更新、奖励、日志和原有结算必须在同一个原子 batch 中提交。参考已有炼丹 `mutation_guards` 实现快照并发保护，并使用数据库唯一索引保护同日重复目标。不得只做“先查数量再写日志”。
- 并发请求下必须保证成功场次不超过 3、同日同目标最多成功 1 场、奖励最多发放 1 次，且不产生部分写入。
- 保留现有认证、CSRF、Origin 保护和项目错误映射，不向前端暴露数据库错误。

测试要覆盖：奖励表的全部边界、3 次上限与第 4 次拒绝、失败/零奖励仍扣次数、UTC+8 跨日重置、同目标二次拒绝且不多扣次数、手动阵容优先与顺序、自动阵容的不重复/归属/受伤弟子、失效手动阵容回退、弟子少于 3 人拒绝、奖励同步写入 state/响应/日志、旧记录兼容、两类并发竞态、前后端契约和现有安全保护。
