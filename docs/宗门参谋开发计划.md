# 宗门参谋开发计划

页面右上角「同步」按钮左边新增「参谋」按钮，点开弹窗，根据宗门现状告诉玩家**下一步该做什么**：
推荐最值得培养的 5 名弟子、每名主力的下一步、建筑升级顺序、资源怎么用、资源获取哪里还能优化。

**纯前端**：只用前端已有的数据（`state`、`hub`、装备视图、日课摘要、门人调度结果）计算，不改服务端、不加接口。
写法照 `apps/web/src/utils/discipleDispatch.ts`（纯函数，不碰 DOM / Vue），测试照 `tests/web/disciple-dispatch.test.ts`。

---

## 1. 产品规则（已和产品确认）

- 入口：右上角「同步」按钮**左边**一个「参谋」按钮（样式与同排 `icon-action` 一致，配一个简单的 svg 图标）；有可执行的建议时按钮右上角显示条数角标（样式参照「更新」按钮的红点 `icon-action-dot`，改成带数字的小角标）。
- 「门人调度」保留不动。
- 主力推荐：**前 5 名**，只显示「推荐培养」标签和理由，**不显示分数**。
- 每条建议都带一个「去处理」按钮，点了打开对应的弹窗或滚动到对应区域（见 2.4）。

## 2. 规则细节

### 2.1 弹窗分区（从上到下）

1. **下一步**：从下面所有建议里按优先级取最重要的 3 条，置顶显示。
2. **弟子培养**：5 名主力卡片（名字、境界、天赋、战力、「推荐培养」标签、理由、这名弟子的下一步）。
3. **建筑**：还能升级的建筑，按收益排序。
4. **资源获取**：产出、岗位、每日收益哪里还能补。
5. **资源使用**：满仓浪费提醒、各资源该花在哪。

每个分区没有建议时显示一句「暂无需要处理的」，不留空白。

### 2.2 主力推荐（前 5 名）

**候选**：全部弟子，排除正在担任执事的（`stewardOffice !== null`，执事不能出战）。

**内部潜力分**（不显示给玩家）：
```
战斗属性 = 攻击 × 0.4 + 防御 × 0.35 + 身法 × 0.25        // 与战力公式的权重一致，用基础属性（不含装备）
境界分   = realmOrder / 8 × 100                           // 炼气 0 … 渡劫 100
潜力分   = 资质 × 0.45 + 战斗属性 × 0.35 + 境界分 × 0.20
         + 战斗天赋（talents.ts 里 category = 'combat' 的天赋）时 +8
```
按潜力分从高到低取前 5（同分按战力高的在前）。

**理由**（挑出最突出的 2～3 条，作为小标签显示）：
- 资质 ≥ 75：「资质 88 · 修炼快」
- 战斗属性里最高的一项 ≥ 75：「攻击 92」
- 战斗天赋：「战意天赋」（用天赋名）
- 境界是全宗前 2：「境界领先」
- 都不满足时：「综合最均衡」

**错配提醒**（放在该弟子卡片里）：资质 ≥ 75、不在修炼岗，而且天赋不是产出类（产出类见 `TALENT_POSTS`）→「资质高，建议改去修炼」。

### 2.3 每名主力的下一步（按顺序取第一条满足的）

| 条件 | 建议 |
|---|---|
| 重伤 / 受伤 | 去疗伤 |
| `canBreakthrough` | 可以突破了 |
| `breakthroughReadyExceptEnergy` | 只差灵气就能突破 |
| 装备格有空（3 格：兵器 / 护甲 / 法器，按装备视图里穿在他身上的装备数） | 装备有空格，去炼器或功勋兑换 |
| 穿着凡品 / 灵品 | 换成宝品以上 |
| 有装备祭炼未到八重 | 祭炼到八重（八重以上不主动建议） |
| `bodyTemperingRemaining > 0` 且有 `bodyTemperingTarget` | 用淬体丹补「防御」等弱项 |
| `aptitudePillRemaining > 0` 且资质 < 80 | 用培元丹提资质 |
| 以上都没有 | 「状态良好，继续修炼」（不计入角标） |

装备视图没加载时，跳过装备相关的两条。

### 2.4 建筑

- 对每个 `level < maxLevel` 的建筑出一条，排序：演武场 → 灵矿 → 聚灵阵 → 藏经阁 → 炼器坊 → 灵药园 → 其他。
- 文案带收益：演武场「战斗力每级 +10%」、灵矿「灵石产出」、聚灵阵「灵气产出」、藏经阁「修炼速度」、炼器坊「更高品质装备」、灵药园「药材产出」。
- `canUpgrade` 为 true：「可以升级」（计入角标）；否则显示 `blockedReason`（不计入角标）。
- 宗门可晋升（`state.sectUpgrade?.canUpgrade`）也放这里：「宗门可晋升，容量与上限都会提高」。

### 2.5 资源获取（产出优化）

每条满足就出一条（都计入角标）：
- 有闲置弟子（`assignment === 'idle'`）→「N 名弟子闲置，派去修炼或岗位」。
- 采灵 / 吐纳岗位没坐满（`state.assignments` 里 `currentCount < maxCount`）→「采灵还空 N 个位置，多一人每小时多约 15 灵石」。
- 门人调度有建议（`dispatchPlan` 的建议数 > 0）→「门人调度有 N 项建议（天赋没在对口岗位）」。
- 执事空缺 →「N 个执事空缺，执事有产出 / 修炼加成」。
- 历练还有空位（看 `state.journey` 的名额字段）→「还能派 N 名弟子历练」。
- 每日收益没拿：日课有可领 / 镇妖塔可扫荡 / 秘境今日还有次数 / 讨伐开放中 / 灵脉无主可进驻 / 拍卖行待领取（数据都在 `hub` 与日课摘要里，与待办同一口径）。
- 灵石产出偏慢：灵矿没满级**且**采灵没坐满 →「灵石来源偏慢：先升灵矿、把采灵坐满」；灵气同理（聚灵阵 / 吐纳）。

### 2.6 资源使用

- 满仓（`capped`）的资源：「X 已满仓，产出在浪费」+ 去处：
  灵石 → 升级建筑 / 祭炼；药材 → 炼丹 / 坊市卖出；矿石 → 炼器 / 坊市卖出 / 赌石；灵气 → 突破；玄铁 → 炼器 / 祭炼。
- 快满（余额 ≥ 容量 90%，未满仓）：同上，文案「快满仓了」。
- 固定一条说明（不计入角标）：「灵石优先顺序：演武场 → 主力突破 → 装备配齐 → 祭炼到八重 → 其他」。

### 2.7 下一步（置顶 3 条）的优先级

满仓浪费 > 演武场可升级 > 主力受伤 > 主力可突破 > 每日收益可领 > 采灵 / 吐纳空位与闲置 > 主力装备空格 > 其他建筑可升级 > 其余。

### 2.8 角标

角标 = 所有「可执行」建议的条数（上面写了不计入的除外），超过 99 显示 99+；0 时不显示。

## 3. 代码结构

- `apps/web/src/utils/advisor.ts`（新，纯函数）：
  - 输入：`{ state, hub, equipment, dailyTasks, dispatchSuggestionCount }`（后三者可能为 null）。
  - 输出：`{ nextSteps, mainDisciples: { discipleId, name, realmName, talentName, combatPower, reasons: string[], nextStep: Suggestion | null, misplaced: string | null }[], buildings, income, spending, badgeCount }`。
  - `Suggestion { id, text, actionLabel, action: AdvisorAction, countsTowardBadge: boolean, priority: number }`。
  - `AdvisorAction` 是一个联合类型：`{ kind: 'panel', panel: ... } | { kind: 'disciple', discipleId } | { kind: 'scroll', target } | { kind: 'dispatch' } | ...`，只描述去哪里，不做跳转。
  - 战斗天赋 id 列表从 `apps/server/src/modules/game/talents.ts` 里 `category: 'combat'` 的那几个抄过来，写成常量并注明来源。
- `apps/web/src/components/AdvisorDialog.vue`（新）：只渲染 `advisor.ts` 的结果；点「去处理」emit `action`。
- `apps/web/src/components/SectScreen.vue`：
  - 右上角加按钮与角标；`openPanel` 增加 `'advisor'`（或单独的 ref），用 `ModalShell` 打开 `AdvisorDialog`。
  - 处理 `action`：关掉参谋弹窗后，复用现有的打开方式（`openPanel.value = ...`、`openDetail(id)`、`openEquipment()`、`openRefineHall()`、`showDispatch = true`、`scrollToSection(...)`、`openBatchHeal(...)` 等，参照 `onTodo` 与 `openHubCard`）。
  - 输入数据用 SectScreen 已有的 `hub`、`equipment`、`dailyTasks`、`dispatchPlan`/`dispatchCount`。
- `apps/web/src/data/changelog.ts`：最前面加一条（id `2026-10-13-advisor`）。

## 4. 测试

`tests/web/advisor.test.ts`（照 `tests/web/disciple-dispatch.test.ts` 造数据）：
- 主力：执事被排除；取前 5；资质 / 战斗属性 / 战斗天赋影响排序；理由标签正确；不输出分数字段。
- 下一步：受伤 > 可突破 > 装备空格 > 低品质 > 祭炼不到八重 > 淬体丹 > 培元丹 的顺序。
- 建筑：排序、可升级与 blockedReason。
- 资源获取：闲置、采灵空位、执事空缺、每日收益、灵石来源偏慢。
- 资源使用：满仓与 90% 快满。
- 角标计数与「下一步」取前 3 的优先级。
- 输入里 hub / equipment / dailyTasks 为 null 时不报错。
