# 弟子管理优化开发计划

## 1. 目标与边界

将弟子管理改为「列表找人、详情管人」：弟子较多时能快速找到目标，查看培养信息并完成操作。本次同时增加私有备注和驱逐，不增加功法、装备、经验系统或新丹药规则。

当前实现：`apps/web/src/components/SectScreen.vue` 的弟子卡片同时放属性、修为、岗位和破境；`AlchemyPanel.vue` 同时负责炼制与全体弟子用药；后端 `view.ts` 已返回境界、资质、攻防速、战力、修为门槛、伤势、岗位、破境条件和淬体预览。`service.ts` 已有 `assignDisciple`、`breakthrough`、`usePill` 和 `SectDraft` 结算/写回流程。守擂阵容存于 `sects.defense_lineup`，挑战记录保存阵容快照。

## 2. 产品规则

### 2.1 列表与进度

每行只展示头像及修为进度环、修为数字、姓名、备注、境界阶段、战力、当前状态和「详情」入口。备注为空时不占用大块空间。

- 所谓「经验值」就是现有 `cultivation / requiredCultivation`，不新增经验字段。进度 clamp 到 0%～100%，并保留可读数字，如 `90/180`。
- `requiredCultivation === null` 显示「已达当前版本上限」，不能把满环解释为可破境。「可破境」只看服务端 `canBreakthrough`；修为满但疗伤/灵气不足可显示「修为已满」，不可误标可操作。
- 状态展示优先级：疗伤中 > 可破境 > 修为已满但暂不可破境 > 当前岗位（含闲置）；岗位信息不能随着精简而消失。详情展示完整伤势、岗位、修为、阻止原因及破境胜算/消耗。
- 可复用现有每秒平滑修为展示，但「可破境」及筛选条件只认最新服务端状态，不能因本地动画达到 100% 擅自启用命令。
- 「详情」按钮可键盘操作且焦点清晰。若整行也可点击，不要在按钮中嵌套按钮。

### 2.2 搜索、筛选、排序

列表上方提供：姓名/备注搜索、境界、岗位、状态（全部、可破境、疗伤、修为已满、闲置）筛选，及排序（默认招募顺序、战力高低、境界高低）。可组合使用；显示 `匹配人数 / 总人数`，提供重置和无结果态。

- 宗门弟子上限仅为几十人，对 `state.disciples` 做前端计算，不新增分页、接口或数据库索引。
- 搜索 trim、不区分大小写、包含匹配；空备注不匹配。境界排序使用现有境界顺序与阶段，不按境界名称字符串排序；相同值保持原顺序。
- 筛选依据服务端现有字段。疗伤按 `injuredUntil > serverNow` 判断，随同步刷新；前端不另造游戏规则。

### 2.3 弟子详情

在现有 `ModalShell` 中显示选中弟子的名字、备注编辑、境界与修为、岗位切换、四轴雷达图、资质/攻防速/天赋/战力、伤势、破境、三种已有丹药服用、驱逐。只存 `discipleId`，每次从最新 `state.disciples` 找对象；操作成功后弹窗保持打开并显示更新值，驱逐成功后关闭。

- 雷达图使用资质、攻击、防御、身法四轴，均以 `1..100` 原值等比绘制。资质影响修炼，并非战力公式的一部分；天赋是类别、战力是派生值，不作为轴。图旁列出精确数值，不能只靠图形传达属性。
- 岗位切换沿用 `/game/assign`，列表不再保留大号岗位选择器；破境沿用 `/game/breakthrough`。显示后端 `canBreakthrough`、`blockedReason`、胜算与灵气消耗，不复制判定公式。
- 炼丹面板保留配方及「炼制」，将全局「弟子用药」入口迁至弟子详情。详情根据库存、伤势、修为及淬体预览显示每种丹药的可用性、效果和禁用原因；服务端 `/game/use-pill` 最终裁决。不要保留两个相互冲突的服药入口，也不改变现有三种丹药规则。
- 窄屏详情与二次确认可滚动且不溢出；沿用 `ModalShell` 的 Esc、遮罩、层级和滚动锁。关闭后焦点尽可能回到触发入口。

### 2.4 私有备注

- 新增 `migrations/0013_disciple_management.sql`：给 `disciples` 增加 `note TEXT NOT NULL DEFAULT ''`，附 `CHECK (length(note) <= 60)`。旧数据迁移后为空串，新招募弟子默认空串。
- 单行纯文本，保存时 trim，允许空串清空；最多 60 个 Unicode 字符，禁止换行和控制字符。服务端严格验证长度与归属，前端提示长度。
- 新增 `POST /api/v1/game/set-disciple-note`，请求 `{ discipleId, note }`，成功返回 `{ state }`。沿用认证、CSRF、Origin、错误封装及现有结算/批量写回。相同内容重复保存不应产生额外游戏效果。
- `note` 只进入登录玩家的 `SectStateView.disciples`；公开宗门档案、排行榜、战报、探索结果不泄漏。

### 2.5 驱逐出师门

- 新增 `POST /api/v1/game/expel-disciple`，请求 `{ discipleId }`，成功返回 `{ state }`。只允许自己的现存弟子；不存在/非本宗统一沿用 `NOT_FOUND`。重复请求不能误删他人。
- 允许驱逐到不足 3 人，甚至 0 人；不返还资源、招募次数或培养成本，不自动降低宗门等级。人数不足 3 人时无法组成主动挑战阵容、也不能被挑战，直至重新招募。相应确认文案需提示。
- 危险操作仅置于详情底部；二次确认必须明确点击「确认驱逐」，取消、关闭、Esc 均不执行。提交中防重复，成功后关闭详情并更新列表及筛选计数。
- 先结算弟子截至当时的修为与岗位收益，再在同一 D1 batch 以 `id + sect_id` 删除弟子。若 ID 在本宗手动守擂阵容内，同批把阵容设为 `NULL`，并提示重新布阵；若不在阵容内，阵容不变。
- `challenge_log` 的独立姓名/战力快照、`sparring_log` 与 `explorations` 历史保留。公开宗门、守擂、招募容量与宗门升级条件应立即反映新人数，不回写历史。
- 不能仅靠前端禁用防并发。提交时至少重新核对弟子仍属本宗、阵容仍与读到的快照一致；复用现有 `mutation_guards` 的 batch 快照守卫。必要时补齐布阵/挑战提交时的成员有效性检查，使驱逐与服药/布阵/挑战交错时不会出现幽灵成功、失效手动阵容或半写；把快照冲突映射为业务错误，不做与本任务无关的大重构。

## 3. 实现顺序

1. **契约与持久化**：0013 迁移、`DiscipleRow` 所有 SELECT、私有 `DiscipleView`、前端类型；备注与驱逐 schema/repository/service/routes；驱逐及阵容的提交守卫。
2. **列表与筛选**：适度拆分 `SectScreen.vue` 的弟子列表与详情组件，复用现有格式化、弹窗、状态/API 模式。筛选与状态派生尽量放在可单测的纯函数中。
3. **详情与操作迁移**：App 统一接管岗位/破境/服药/备注/驱逐动作，以服务端完整 `state` 更新。炼丹面板仍可炼制，移除全局用药建议。
4. **回归与视觉核对**：补 Worker+D1 集成测试、筛选纯函数测试；核对桌面和窄屏、长姓名/备注、空列表、0/满修为、疗伤与弹窗焦点。

不修改公共游戏配置、战力/突破/炼丹公式、挑战奖励与次数。不引入新全局状态库、图表框架或路由。静态四轴雷达可用轻量 SVG 绘制，但须有可访问的数值文本和稳定响应式尺寸。

## 4. 测试与验收

### 服务端与数据库

- 迁移兼容已有弟子；新弟子备注默认空。备注保存/清空后重进 sync 正确；超长、换行、非法 ID、非本宗被拒绝；公开档案不泄漏。
- 驱逐后数据库行消失；返回及再次 sync 的人数、岗位人数/产量、招募容量、宗门升级要求、公开档案正确。不发奖、不返资源和招募次数。重复/跨宗驱逐无副作用。
- 驱逐阵容成员清空阵容；非成员保留阵容。少于 3 人时挑战拒绝且不扣次数，补齐人数后可重新布阵；旧战报仍显示当时的弟子姓名、战力、胜负。
- 结算、删除、阵容更新同一原子提交，失败不留下半写；覆盖与服药、布阵、挑战的关键并发或过期快照。既有突破、服药、招募、秘境与鉴权测试继续通过。

### 前端与交互

- 列表只有指定摘要字段，进度环有数值，满级与可破境状态区分；搜索、组合筛选、排序、重置、无结果均正确。
- 详情始终对应所选弟子的最新状态；雷达图与精确数值一致；岗位、破境、三种丹药、备注和炼制正常；长文案/窄屏不溢出。
- 驱逐有取消、确认、提交中、成功关闭和失败保留详情的完整状态；未确认不写库，驱逐筛选结果最后一人有正确空态。

验收命令：`npm run test:unit`、`npm run typecheck`、`npm run build`、`git diff --check`。如果当前环境无法做浏览器视觉核对，交付时说明未核对的视口与剩余风险。不要自动提交或推送。

## 5. 交付与复审

开发者交付时报告：改动文件、迁移与接口、关键取舍、上述命令的真实结果、视口检查和遗留问题，并保留最终 diff。后续复审重点检查跨宗权限、备注私密性、驱逐并发与阵容一致性、历史兼容、前端状态和移动端布局。
