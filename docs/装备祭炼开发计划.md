# 装备祭炼开发计划

> 装备的长期养成：消耗灵石 / 矿石 / 玄铁提升装备的「重」数（0～12）。
> 失败只扣材料，不降级、不碎装备；同一宗门冲同一重连续失败会悄悄提高成功率（不展示）。
> 本文是**给实现者的施工图**：每一步改哪个文件、加什么函数、数值是多少都写死了，照做即可；
> 文中没写的东西**不要做**（见第 9 节「不做 / 不许改」）。

## 1. 已确认的规则

| 项 | 规则 |
|---|---|
| 名称 | 功能叫「祭炼」；等级叫「重」：一重 … 十二重 |
| 解锁 | 与炼器相同：宗门 2 级（复用 `requireForgeUnlocked`） |
| 上限 | 所有品质都是 **12 重** |
| 对象 | 背包里的、穿在弟子身上的都能祭炼；穿在**在外历练 / 重伤卧床**弟子身上的不能（复用 `requireNotAway`） |
| 一次 | 每次请求只冲 1 重（当前重数 + 1） |
| 成功 | 重数 +1，主属性 / 副属性 / 战力加成按第 2 节增加（**直接写进装备行**） |
| 失败 | 只扣材料；重数、属性都不变；不碎装备、不降级 |
| 隐藏补偿 | 宗门级、按「目标重数」分开计数：冲第 N 重失败 → 该宗门「第 N 重失败次数」+1；任何装备冲第 N 重成功 → 该计数清零。成功率 = min(上限, 基础 + 次数 × 每次加成)。**不在任何接口 / 界面 / 日志里出现** |
| 分解 | 返还**只按品质**（与现在一样），祭炼花的材料不退 |
| 拍卖 | 祭炼重数跟着装备走（上架 → 成交 / 流拍 / 下架退回都保留重数） |
| 起拍价下限 | 不变（只按品质） |
| 显示 | 装备名不改（库里仍是「仙品·赤霄剑」）；名字后面单独显示「七重」标签：一～八重普通色，九～十一重紫色，十二重赤金 |

## 2. 数值（全部写死在代码表里，不要用公式现算）

### 2.1 每重成功率（基点，10000 = 100%）

| 冲到 | 基础 | 每次失败加 | 上限 |
|---|---|---|---|
| 1 | 10000 | 0 | 10000 |
| 2 | 10000 | 0 | 10000 |
| 3 | 10000 | 0 | 10000 |
| 4 | 9000 | 500 | 10000 |
| 5 | 8000 | 500 | 9500 |
| 6 | 6500 | 500 | 8500 |
| 7 | 5500 | 400 | 7500 |
| 8 | 4500 | 400 | 6500 |
| 9 | 3500 | 300 | 5500 |
| 10 | 3000 | 300 | 4800 |
| 11 | 2500 | 200 | 4000 |
| 12 | 2000 | 200 | 3500 |

- 成功率 = `min(上限, 基础 + 失败次数 × 每次加成)`
- 判定：`random() * 10000 < 成功率` 即成功（random 是注入的 `() => number`，取值 [0, 1)）
- 失败次数存库时夹到 **最多 50**（`REFINE_FAILS_CAP = 50`）

|---|---|---|---|---|
| 1 | 12 / 9 / 0 | 20 / 15 / 0 | 28 / 21 / 0 | 40 / 30 / 0 |
| 2 | 17 / 14 / 0 | 28 / 23 / 0 | 39 / 32 / 0 | 55 / 45 / 0 |
| 3 | 23 / 18 / 0 | 38 / 30 / 0 | 53 / 42 / 0 | 75 / 60 / 0 |
| 4 | 33 / 27 / 0 | 55 / 45 / 0 | 77 / 63 / 0 | 110 / 90 / 0 |
| 5 | 45 / 36 / 0 | 75 / 60 / 0 | 105 / 84 / 0 | 150 / 120 / 0 |
| 6 | 68 / 45 / 1 | 113 / 75 / 1 | 158 / 105 / 1 | 225 / 150 / 1 |
| 7 | 90 / 54 / 1 | 150 / 90 / 1 | 210 / 126 / 1 | 300 / 180 / 2 |
| 8 | 113 / 72 / 1 | 188 / 120 / 2 | 263 / 168 / 2 | 375 / 240 / 3 |
| 9 | 147 / 90 / 1 | 245 / 150 / 2 | 343 / 210 / 3 | 490 / 300 / 4 |

| 11 | 225 / 135 / 2 | 375 / 225 / 3 | 525 / 315 / 4 | 750 / 450 / 6 |
| 12 | 282 / 162 / 2 | 470 / 270 / 4 | 658 / 378 / 6 | 940 / 540 / 8 |

资源 id：灵石 `spiritStone`、矿石 `ore`、玄铁 `xuantie`（已有常量 `XUANTIE_RESOURCE_ID`）。

### 2.3 每重成功后的增量

**主属性增量**（冲到第 N 重成功时加）：

| 品质 | 冲 1～5 重 | 冲 6～12 重 |
|---|---|---|
| 凡品 | +1 | +1 |
| 灵品 | +2 | +3 |
| 宝品 | +2 | +3 |
| 仙品 | +3 | +4 |

**副属性增量**（只有两次，其余各重为 0）：

| 品质 | 冲到 5 重时 | 冲到 12 重时 |
|---|---|---|
| 凡品 | +1 | +2 |
| 灵品 | +2 | +3 |
| 宝品 | +3 | +4 |
| 仙品 | +4 | +6 |

**战力加成**（每件装备，按**当前重数**算的累计值，基点；与品质加成相加）：

| 当前重数 | 0～8 | 9 | 10 | 11 | 12 |
|---|---|---|---|---|---|
| 祭炼战力加成 | 0 | 100 | 200 | 300 | 600 |

（九重起「通灵」每重 +1%；十二重「圆满」另加 2%。品质加成不变：凡 200 / 灵 400 / 宝 700 / 仙 1000。）

例：仙品十二重 = 1000 + 600 = 1600 基点。

## 3. 数据库：新迁移 `migrations/0044_equipment_refine.sql`

文件名必须是 `0044_equipment_refine.sql`（当前最新是 0043）。内容照抄：

```sql
-- Migration number: 0044 	 Name: equipment_refine
--
-- 装备祭炼（docs/装备祭炼开发计划.md）：
--   equipment.refine_level <- 祭炼重数 0~12；成功时与 main_value / sub_value 一起写（增量直接写进数值列）。
--   equipment_refine_fails（新表）<- 每宗门「冲第 level 重」的连续失败次数（隐藏的成功率补偿）。

--   以后调上限不必重建表（SQLite 不能就地改 CHECK，见 0020 / 0033 的说明）。

-- - 宗门不会被删除：sect_id 不建 CASCADE（与 0042 同一做法）。

ALTER TABLE equipment ADD COLUMN refine_level INTEGER NOT NULL DEFAULT 0
  CHECK (refine_level >= 0);

CREATE TABLE equipment_refine_fails (
  sect_id TEXT NOT NULL,
  level INTEGER NOT NULL CHECK (level >= 1),
  fails INTEGER NOT NULL DEFAULT 0 CHECK (fails >= 0),
  updated_at INTEGER NOT NULL,
  PRIMARY KEY (sect_id, level)
);
```

不要改 `apps/server/src/infra/db/readiness.ts` 的 `REQUIRED_TABLES`（近几次新表都没加，保持一致）。

| 函数 | 说明 |

### 4.5 命令：`service.ts` 新增 `refineEquipment`

放在 `salvageEquipment` 后面。照着 `unequipItem` / `salvageEquipment` 的写法：

```ts
export interface RefineEquipmentOutcome {
  equipmentId: string;
  name: string;
  success: boolean;
  /** 祭炼前 / 后的重数（失败时两者相等）。 */
  fromLevel: number;
  toLevel: number;
  /** 本次实际扣掉的材料（最小单位字符串）。 */
  cost: Record<string, string>;
}

export async function refineEquipment(
  db: D1Database, userId: string, equipmentId: string, now: number,
): Promise<{ state: SectStateView; outcome: RefineEquipmentOutcome }>
```

步骤（顺序不能乱）：

1. `const draft = await draftFor(db, userId, now);` → `requireForgeUnlocked(draft);`
2. `const { items } = await loadEquipment(db, draft.sect.id);` 找 `equipmentId`，没有 → `AppError('NOT_FOUND', '装备不存在')`。
3. `isEquipmentQuality(item.quality)` 为 false → `AppError('INVALID_STATUS', '这件装备不能祭炼')`。
4. `const fromLevel = Number(item.refine_level ?? 0);` 若 `fromLevel >= REFINE_MAX_LEVEL` → `AppError('INVALID_STATUS', \`${item.name}已祭炼至十二重圆满\`)`。
5. 穿在弟子身上：`const holder = item.disciple_id === null ? null : draft.discipleById(item.disciple_id);`，`holder !== null` 时 `requireNotAway(draft, holder, '祭炼装备')`。
6. `const target = fromLevel + 1; const cost = refineCostUnits(item.quality, target);`
   对 cost 的每一项 `draft.requireResource(resourceId, amount)`（余额不足时它会抛错并带资源名，不用自己写提示）。
7. `const fails = await new EquipmentRepository(db).findRefineFails(draft.sect.id, target);`
8. `const success = rollRefine(target, fails, Math.random);`
9. 失败次数：`const nextFails = nextRefineFails(fails, success);` 只有 `nextFails !== fails` 时才 `draft.addStatement(upsertRefineFailsStatement(draft.sect.id, target, nextFails, now))`。
10. 成功时：
    - `mainValue = Number(item.main_value) + refineMainGain(quality, target)`，`subValue = Number(item.sub_value) + refineSubGain(quality, target)`；
    - `draft.addStatement(updateEquipmentRefineStatement({ ... refineLevel: target, mainValue, subValue }))`；
    - `holder !== null` 时：`const nextItems = items.map((row) => row.id === item.id ? { ...row, refine_level: target, main_value: mainValue, sub_value: subValue } : row);` 然后 `applyGearRefresh(draft, holder.id, nextItems);`（**必须在 update 语句之后**加，SUM 才看得到新值）。
11. 提交（装备行进守卫，防止同时被上架 / 卸下）：
    - `holder !== null` → `await draft.commitDisciple([{ id: holder.id }], undefined, { equipmentItems: [{ id: item.id, discipleId: item.disciple_id }] });`
    - 否则 → `await draft.commit({ equipmentItems: [{ id: item.id, discipleId: null }] });`
    并发说明：每次祭炼都扣资源，两种 commit 都带资源余额快照守卫，同一时刻的第二次请求会整批回滚并报「宗门状态已变化，请刷新后重试」，不需要另写守卫。
12. 成功且 `target === REFINE_MAX_LEVEL` 且品质是 `immortal` 时，提交**之后**广播：
    `await broadcastWorldBoss(db, \`【祭炼】${draft.sect.name}将 ${item.name} 祭炼至十二重圆满！\`, now);`（与炼器出仙品的广播同一个函数）。
13. 返回 `{ state: draft.view(), outcome: { equipmentId, name: item.name, success, fromLevel, toLevel: success ? target : fromLevel, cost: 把 cost 的值 String() } }`。

**禁止**：在 outcome / 视图 / 事件日志 / console 里输出 `fails`、`nextFails` 或「实际成功率」。
