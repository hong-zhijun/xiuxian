# 宗门日课（每日任务）开发计划

每天给宗门 5 个小任务，完成后领灵石；5 个都领完再开一个日课宝箱（玄铁 / 神木 / 丹药）。
目的：给每天上线的玩家一份稳定的灵石来源，同时把玩家引向各个现有玩法。

金额一律是**最小单位**（1 展示单位 = 1000 最小单位）。「今天」= UTC+8 自然日，用 `dateKeyUtc8(now)` 与 `dayStartMs(now)`（都在 constants.ts）。

---

## 1. 产品规则（已和产品确认，不要改数字）

### 1.1 任务池

进度**全部从现有记录统计**，不在其它玩法里加任何计数代码。

| id | 名称 | 目标 | 进度来源（本宗、今天） | 出现条件 | 类别 |
|---|---|---|---|---|---|
| `bossHit` | 讨伐出手 | 3 | `world_boss_hits` 行数（`sect_id`，`created_at ≥ 今天 0 点`） | 无 | 普通 |
| `explore` | 秘境探索 | 2 | `explorations` + `realm_explorations` 行数（`sect_id`，`created_at ≥ 今天 0 点`） | 宗门已建演武场（`arenaHall`） | 普通 |
| `challenge` | 登门挑战 | 1 | `challenge_log` 行数（`attacker_sect_id`，`created_at`） | 无 | PvP |
| `towerClimb` | 镇妖塔闯塔 | 1 | `sect_towers`：`fail_date_key` = 今天且 `fail_count > 0`，或 `max_floor_at ≥ 今天 0 点` → 1（赢输都算） | 宗门 ≥ `TOWER_UNLOCK_SECT_LEVEL` | 普通 |
| `gamble` | 赌坊玩法 | 3 | `sects.debate_count`（`debate_date_key` = 今天才算，否则 0） | 宗门 ≥ `GAMBLING_UNLOCK_SECT_LEVEL` | 普通 |
| `journey` | 派弟子历练 | 1 | `disciple_journeys` 行数（`sect_id`，`started_at ≥ 今天 0 点`） | 无 | 轻松 |
| `towerSweep` | 镇妖塔扫荡 | 1 | `sect_towers.sweep_date_key` = 今天 → 1，否则 0 | 宗门 ≥ `TOWER_UNLOCK_SECT_LEVEL` 且 `max_floor > 0` | 轻松 |
| `recruit` | 招募弟子 | 1 | `sects.recruit_count`（`recruit_date_key` = 今天才算，否则 0） | 弟子数 < 宗门弟子上限 | 轻松 |
| `stockTrade` | 灵股交易 | 1 | `stock_trades` 行数（`sect_id`，`created_at`） | 宗门 ≥ `MARKET_UNLOCK_SECT_LEVEL` | 轻松 |
| `veinAttack` | 灵脉抢夺 | 1 | `vein_battles` 行数（`attacker_sect_id`，`created_at`） | 宗门 ≥ `VEIN_UNLOCK_SECT_LEVEL` | PvP |

进度显示为 `min(实际次数, 目标)`。列名以迁移文件为准，写代码前逐个核对（`migrations/` 里 `CREATE TABLE` 的最新一版）。

### 1.2 每天抽 5 个

- 每宗门每天**第一次**读取日课时抽出 5 个任务并**落库**（之后一整天不变，即使中途宗门升级解锁了新玩法）。
- 只从「出现条件」满足的任务里抽。
- 约束：**至少 2 个「轻松」**（不够 2 个可选时有几个算几个），**最多 1 个「PvP」**。
- 可选任务不足 5 个时，有几个给几个。
- 随机源：用宗门 id + 日期键算种子（复用 `market.ts` 的 `seedNumberOf` 或现有同类哈希），纯函数里用种子驱动的伪随机抽取，便于测试。

### 1.3 奖励

- **单个任务**：完成后可领，`宗门等级（领取时）× 50` 灵石 = `level × 50 × 1000` 最小单位。
- **日课宝箱**：当天抽到的任务**全部已领取**后可开，内容：
  - 玄铁 3~5 个（均匀随机整数）
  - 神木 1~2 个
  - 丹药 1 颗：从 `healingPill` / `cultivationPill` / `bodyTemperingPill` 里均匀随机
- 资源入账用 `draft.grantResource`（不夹容量，与赌石同口径）；丹药用 `draft.addPill`。
- 每个任务、宝箱每天只能领一次；跨天未领的作废（不补发）。

## 2. 代码结构（照现有写法）

### 2.1 纯规则 `apps/server/src/modules/game/dailyTasks.ts`（新）

不读库、不取时间，随机源 / 种子从参数传入（文件头写法照 `tower.ts`、`stoneGamble.ts`）。

- `DAILY_TASKS`：1.1 的表（id、name、target、category: `'easy' | 'normal' | 'pvp'`）。
- `DAILY_TASK_COUNT = 5`、`DAILY_TASK_STONE_PER_LEVEL = 50`、宝箱常量（玄铁 3~5、神木 1~2、丹药候选）。
- `pickDailyTasks(availableIds, seed): DailyTaskId[]`：按 1.2 规则抽取，结果顺序稳定。
- `dailyTaskReward(sectLevel)`：单个任务的灵石（最小单位）。
- `rollDailyChest(random)`：返回 `{ xuantie, shenmu, pillId }`（展示单位整数 + 丹药 id）。

### 2.2 迁移 `migrations/0048_daily_tasks.sql`

文件头格式照 `migrations/0044_equipment_refine.sql`。

```
daily_tasks(
  sect_id TEXT NOT NULL,
  date_key TEXT NOT NULL,
  tasks TEXT NOT NULL,                 -- JSON 数组：当天抽到的任务 id（顺序即展示顺序）
  claimed TEXT NOT NULL DEFAULT '[]',  -- JSON 数组：已领取的任务 id
  chest_claimed INTEGER NOT NULL DEFAULT 0 CHECK (chest_claimed IN (0, 1)),
  version INTEGER NOT NULL DEFAULT 0 CHECK (version >= 0),
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL,
  PRIMARY KEY (sect_id, date_key)
)
```

sect_id 不建 CASCADE（同 0042 / 0044）。旧日期的行不清理也没关系（每宗门每天一行）。

### 2.3 Repository（`repository.ts`）

- `DailyTaskRepository`：`find(sectId, dateKey)`、以及**一个**统计今天各来源次数的方法（可以一次 SQL 用多个子查询返回所有计数，减少 D1 往返）。
- `insertDailyTasksStatement(...)`（`INSERT ... ON CONFLICT (sect_id, date_key) DO NOTHING`）。
- `updateDailyTasksClaimStatement(sectId, dateKey, claimed, chestClaimed, nextVersion, now)`。
- 并发守卫 `dailyTasksGuardStatement(guardId, sectId, dateKey, version)`：**照 `sectTowerGuardStatement`**（约 3453 行）写，没有行按 0。

### 2.4 Service（`service.ts`）

三个导出函数，都先 `const draft = await draftFor(db, userId, now)`（顺带结算，返回 state）：

1. `getDailyTasks(db, userId, now)`：
   - 读今天的行；没有就算出可选任务 → `pickDailyTasks` → 写入（单独执行 insert 语句即可，`ON CONFLICT DO NOTHING` 后再读一次，保证并发首读也只有一份）。
   - 统计进度，返回 `{ state, dailyTasks: DailyTasksView }`。
2. `claimDailyTask(db, userId, taskId, now)`：
   - 任务不在今天的列表 → `VALIDATION_ERROR`；已领 → `INVALID_STATUS`（「今天已经领过了」）；进度未达标 → `INVALID_STATUS`（「任务还没完成」）。
   - `draft.grantResource('spiritStone', dailyTaskReward(level))`；写回 claimed + version+1；
   - `await draft.commit({ extraGuards: [{ id, statement: dailyTasksGuardStatement(...) }] })`（照 `sweepTower` 约 10464 行的写法）。
   - 返回 `{ state, dailyTasks, result: { taskId, spiritStone, message } }`。
3. `openDailyChest(db, userId, now)`：
   - 今天的任务没有全部领完 → `INVALID_STATUS`；宝箱已开 → `INVALID_STATUS`。
   - `rollDailyChest(Math.random)` → `grantResource` 玄铁 / 神木、`addPill`；写回 chest_claimed = 1 + version+1。
   - commit 时同时带上丹药守卫（照 `wheelSpin` 的 pill 快照写法，或 `commit({ pillId, extraGuards })`，以 `SectDraft.commit` 实际支持的参数为准）。
   - 返回 `{ state, dailyTasks, result: { xuantie, shenmu, pillId, pillName, message } }`。

### 2.5 Schema / 路由

- `GET /game/daily-tasks` → `respondOk(c, { state, dailyTasks })`
- `POST /game/daily-tasks/claim`，body `{ taskId }`（`z.strictObject`，taskId 用 `z.enum(DAILY_TASK_IDS)`）
- `POST /game/daily-tasks/chest`，body `{}`（`z.strictObject({})`）

### 2.6 视图（`view.ts`）

```
DailyTasksView {
  dateKey: string;
  tasks: { id, name, target, progress, completed: boolean, claimed: boolean, reward: number /* 最小单位灵石 */ }[];
  chest: { available: boolean; claimed: boolean; description: string /* 「玄铁 3~5、神木 1~2、随机丹药 1 颗」 */ };
}
```

不放进 `/game/sync`（每次同步都统计会多出 D1 读取），只由日课接口返回。

### 2.7 前端

- `apps/web/src/api/game.ts`：类型与三个请求函数（照 `shopBuy` / `fetchMeritShop` 的写法）。
- 新组件 `apps/web/src/components/DailyTasksCard.vue`：首页卡片，挂载时 `GET /game/daily-tasks`。
  - 每个任务一行：名称、进度条 `progress/target`、奖励灵石、按钮（未完成「进行中」禁用 / 完成「领取」 / 已领「已领取」）。
  - 底部宝箱按钮：未满足时禁用并写「领完 5 个任务后可开」，开启后显示获得内容。
  - 有可领取的任务或可开的宝箱时，卡片标题旁显示小红点。
  - 领取成功：把回执里的 state 交给上层（照 `ShopDialog` → `SectScreen.handOffShopState` 的方式：emit 新 state，SectScreen 用 `emit('recruited', next)`），并 `notify` 成功文案。
  - 宽度 360px 以下不横向溢出。
- `apps/web/src/components/SectScreen.vue`：在首页合适位置（与祭炼卡片同区域）放入 `DailyTasksCard`。
- `apps/web/src/data/changelog.ts`：最前面加一条（id `2026-10-12-daily-tasks`）。

## 3. 测试

### 3.1 规则测试 `tests/game/daily-tasks-rules.test.ts`

- `pickDailyTasks`：同一种子结果相同；结果无重复；数量 = min(5, 可选数)；至少 2 个轻松（可选的轻松 ≥ 2 时）；PvP 最多 1 个；只从可选里抽。
- `dailyTaskReward(10)` = 500000。
- `rollDailyChest`：注入固定 random 覆盖上下界（玄铁 3 / 5、神木 1 / 2、三种丹药）。

### 3.2 接口测试 `apps/server/test/daily-tasks.test.ts`

建宗门 / 改余额 / 冻结结算的工具照 `apps/server/test/shop.test.ts`。直接往来源表插记录来制造进度（例如插 `sparring_log` 行、改 `sects.recruit_count` 与 `recruit_date_key`）。

- 首次 GET 生成 5 个（或可选数个）任务，再次 GET 不变。
- 进度统计：每种来源至少覆盖一次（插昨天的记录不计入）。
- 领取：未完成 → `INVALID_STATUS`；完成后领取 → 灵石 + 等级×50×1000；重复领取 → `INVALID_STATUS`；不在今天列表的 taskId → 400 或 `VALIDATION_ERROR`。
- 宝箱：未领完 → `INVALID_STATUS`；领完后开启 → 玄铁 3~5、神木 1~2、丹药 +1；重复开 → `INVALID_STATUS`。
- 跨天：把行的 `date_key` 改成昨天后再 GET，生成新的一天，旧的领取状态不带过来。
