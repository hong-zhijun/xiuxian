# 弟子历练开发计划

## 1. 目标与范围

新增单人、定时的弟子历练。玩家选择一名已筑基的弟子、历练方向和时长；出发期间该弟子暂停原岗位产出与正常修炼，到期按服务器时间归队，获得修为、资源，并可能受伤。它是用弟子的时间换收益的挂机决策，不是现有的即时秘境探索，也不组队。

本计划以当前代码为准：`service.ts` 的 `SectDraft` 在每次 sync/命令前调用 `settleEconomy`；`settle.ts` 有全宗门共用的 12 小时离线收益上限；`DiscipleDetailDialog.vue` 管理单个弟子，`App.vue` 接管写请求并回填完整 `state`。实现前先读这些文件及现有的驱逐、布阵、探索和挑战路径。

本次不做取消、加速、付费、掉落道具、历练队伍、丹药新效果、定时 Worker/Cron 或玩家间交易。历史记录只在本宗可见。

## 2. 第一版产品规则

### 2.1 资格与名额

- 门槛按**弟子本人**判定：`realmIndex(realm_id) >= realmIndex('foundationEstablishment')`，筑基初期起可参加，更高境界亦可；炼气弟子不可派出。宗门等级不是代替弟子境界的门槛。
- 受伤未愈、已经在外、或有完成但尚未领取资源的历练记录的弟子不可再次出发；每名弟子最多一条未领取记录。
- 同一宗门最多同时有 2 名**尚未到期**的弟子在外；已到期但待领取的记录不占同时历练名额。历练无需每日次数和入场费，代价是原岗位收益。
- 为避免“全员出门使宗门无法被挑战”的免战策略，出发后至少留 3 名不在外的弟子；手动守擂阵容里的弟子不可出发，可先调整阵容。阵容不足 3 人时显示明确阻止原因。自动守擂只从未在外的弟子中选人。
- 出发时由服务端验证归属、境界、伤势、名额、守擂约束与方向/时长。详情页的按钮和原因只是预览，不能替代服务端校验。

### 2.2 方向、时长和结果

固定两种方向、两档时长；数值是第一版测试基线，所有存储资源数量均为最小单位（展示值乘 1000），放在新的服务端纯规则模块中，不在前端重复硬编码。

| 方向 | 时长 | 基础修为 | 基础资源 | 基础受伤概率 |
| --- | ---: | ---: | --- | ---: |
| 访道 | 2 小时 | 180 | 灵石 15000 | 5% |
| 访道 | 6 小时 | 540 | 灵石 45000 | 8% |
| 采集 | 2 小时 | 40 | 药材 25000、矿石 20000 | 12% |
| 采集 | 6 小时 | 120 | 药材 75000、矿石 60000 | 15% |

- 修为按出发时资质套用当前修炼系数 `min(8000 + 40 * aptitude, 20000) / 10000`；修炼天赋额外 `+20%`。采药/炼矿天赋分别使采集中的药材/矿石 `+20%`。每步向下取整，测试明确取整口径；不叠加藏经阁的原岗位静修加成。
- 上述资质/天赋加成后的奖励是保底值。另有独立的 15%“额外收获”判定，触发则修为和各项资源再加各自保底值的 50%（逐项向下取整）。受伤与额外收获独立，二者可同时发生；没有“失败后奖励归零”的分支。随机源可注入测试；在**出发时**按弟子属性快照抽取并保存结果，但只在到期后向前端揭示，刷新/重复领取不能重抽。
- 受伤概率以表格数值为起点，按出发时 `discipleCombatPower` 每满 50 点减 1 个百分点；访道最低 2%，采集最低 5%。受伤者 `injured_until = ends_at + 30 分钟`，从到期而非领取时间起算。晚登录可能已痊愈，但历练记录仍显示受伤结果；现有回春丹可处理尚未结束的伤势。
- 出发前服务端预览保底修为、资源、额外收获概率、实际受伤概率、返回时间，以及名额/不可出发原因；不展示随机结果。预览的修为须按当前剩余突破门槛截断并标注“最多”，实际入账以返程时的剩余门槛为准。访道要求当前阶段仍有修为门槛（`requiredCultivation !== null` 且当前未满），采集对最高阶段仍可用，其修为收益为 0。
- 修为不跨越当前阶段的突破门槛，不自动突破；最高阶段修为保持原值。资源奖励按现有秘境/挑战的直接入账规则允许暂时超过容量，不产生负余额、不借由历练提升资质或天赋。

### 2.3 在外、返程与领取

- 出发前先把旧岗位收益结算到出发时刻；数据库保留原 `disciples.assignment`，历练表记录原岗位快照。**不**往岗位配置里插入假岗位：在外期间由结算和状态视图暂时屏蔽此弟子的岗位产出、静修与占用中的操作，原岗位名额（包括采灵岗位）仍为他保留。
- 在外不可转岗、突破、服药、驱逐、再次历练、主动秘境探索或挑战，也不可进入新守擂阵容；已出发弟子不得被自动守擂选中。保存私有备注可以继续使用。所有相关写路径在服务端检查，不能只禁用按钮。
- `ends_at` 是逻辑返程时间。无论玩家何时上线，结算必须在此时间切开：`[出发, ends_at)` 不得计原岗位收益，`[ends_at, 之后)` 恢复原岗位收益。到期不等用户领取才归队，不依赖浏览器计时器或 Cron。
- 到期后的第一次 sync 或任一游戏写请求，在同一原子批次将历练修为按**返程时的阶段门槛**入账、记录实际增加量与伤势，并标记完成。修为先于返程后的正常静修结算，避免玩家晚领取时修为奖励被静修占满门槛；伤势截止时间固定为 `ends_at + 30 分钟`，不能覆盖其他更晚的伤势，重复同步也不能重置或覆盖随后服用回春丹的效果。
- 资源在玩家领取时一次性入账，并标记 `claimed_at`；领取前不占容量，领取后返回完整最新状态和实际结果。完成未领取的弟子已归队，可以正常工作和进行其他操作，但不能再次历练或被驱逐，须先领取。领取失败不改资源/记录；重复领取不得重复发奖。
- 领取与完成可能在同一请求发生（直接请求领取，未先 sync）。按“旧岗位结算/到期归队及修为伤势/返程后结算/领取资源”顺序处理，保证资源、修为、伤势、完成标记和领取标记不会部分写入。若领取前已有别的游戏请求，完成步骤只执行一次。
- 12 小时离线收益上限保持**整次结算**一个窗口，不可对每个分段分别给 12 小时；超过上限的普通岗位/静修收益仍丢弃，但已按日程完成的历练奖励不能因玩家晚登录而消失。随机事件也只按该次有效时长统一抽取/封顶，不能因分段重复触发。

## 3. 持久化与并发

新增迁移 `migrations/0014_disciple_journeys.sql`，不要改写旧迁移。新表建议包含：`id`、`sect_id`、`disciple_id`、`disciple_name` 快照、`direction`、`duration_seconds`、`original_assignment`、`started_at`、`ends_at`、`completed_at`（未处理返程为 `NULL`）、`claimed_at`、出发时确定但到期前不公开的修为/资源奖励快照与额外收获/受伤结果、`cultivation_awarded`（实际入账，未完成为 `NULL`）。时间用 UTC 整数毫秒，资源快照为受控 JSON；加 `CHECK` 约束及按宗门/弟子/结束时间的查询索引。

- 历史即使弟子日后被驱逐也要留存姓名和结果，`disciple_id` 不对 `disciples` 设级联删除外键。只允许已领取后驱逐。
- 对 `disciple_id` 建 `claimed_at IS NULL` 的**唯一部分索引**，堵住同一弟子重复出发；历史记录不受限。另需在 batch 提交时复核宗门同时在外人数、可守擂人数、弟子境界/伤势/岗位/归属及守擂阵容快照，堵住不同弟子并发出发绕过两人上限。
- 复用 `mutation_guards` + 一次 D1 `batch` 的现有模式；开始、自动返程、领取都要有条件更新/快照守卫。将约束冲突映射为 `INVALID_STATUS` / `CAPACITY_FULL` 等业务错误，不泄露 SQL；不得用“先 SELECT，再无条件 UPDATE”保证只领一次。
- 与现有驱逐、派工、破境、服药、布阵、探索、挑战交错时，任何一个动作要么基于最新“在外”状态被拒绝，要么在快照冲突后整个批次回滚。被动挑战还须检查守方弟子的实时在外状态；跨宗读取只用于安全裁决，不公开他人的历练结果。

## 4. 后端与接口设计

1. 在 `apps/server/src/modules/game/journey.ts` 放方向/时长定义、奖励计算、概率、预览与纯时间规则；在 `settle.ts` 实现可测试的按时间边界结算，保持余额余数、容量、事件数和 12 小时上限一致。不要通过循环多次调用现有 `settleEconomy` 来获得多份 12 小时额度或多批随机事件。
2. `repository.ts` 新增历练行类型、按宗门加载活跃/待领取及最近 10 条历史、条件写入/返程/领取语句及所需守卫；`service.ts` 的 `loadSnapshot`/`SectDraft` 统一处理到期历练。所有会读取或改变弟子出战资格的服务复用同一在外判定。
3. 新增严格 schema 和接口（均需已有会话；POST 继续走 Origin/CSRF）：`GET /api/v1/game/journey-preview?discipleId=...` 返回两个方向、两档时长的预览和阻止原因；`POST /api/v1/game/start-journey` 请求 `{ discipleId, direction, durationSeconds }` 返回 `{ state }`；`POST /api/v1/game/claim-journey` 请求 `{ journeyId }` 返回 `{ state, outcome }`。预览是只读，不做挂机结算，最终资格以 POST 为准。
4. `SectStateView` 与前端同名类型增加宗门历练名额（`activeCount/maxConcurrent`）、每个弟子的历练状态（`none/active/ready`，包含 `journeyId`、`endsAt`、`canStart`、`blockedReason`，不要向未到期状态泄漏结果）及仅自己可见的最近 10 条历练摘要。页面不复制资格公式；状态来自服务端，倒计时仅作展示。
5. `buildSectStateView` 的当前资源/修为速率必须按 `serverNow < endsAt` 屏蔽仍在外的弟子，归队后立即恢复。`assignments.currentCount` 仍按保留的原岗位计算；预览、详情和列表的状态要一致。

## 5. 前端交互

- 在 `DiscipleDetailDialog.vue` 增加“历练”区域：未筑基显示“筑基后可历练”；受伤、名额已满、在守擂阵容等显示服务端原因；可出发时选择方向和时长，显示服务端预览并确认出发。
- 在 `DiscipleRoster.vue` 给在外弟子展示方向和预计返程时间，给已归队待领取弟子展示明确入口；弟子详情可查看返程结果并领取。最近记录最多展示 10 条，受伤与额外收获用文字明确标出，不能仅靠 Toast。
- `SectScreen.vue` 转发开始/领取事件，`App.vue` 通过现有 `busy` 门闩调用 API 并用返回的完整 `state` 更新。出发与领取的失败保留当前弹窗和选择，不产生乐观收益。受伤后现有丹药、探索与破境状态应正确刷新。
- 倒计时按服务端 `serverNow` 校准，归零时触发一次 sync（或最多等待现有 60 秒轮询），切回标签页也刷新；前端倒计时不能自行发奖或把未同步状态判定为可领取。桌面/窄屏均应检查弹窗尺寸、长姓名、已满修为和多条记录。

## 6. 实施顺序与验收

1. 写纯规则及边界测试：筑基门槛、方向/时长白名单、奖励/天赋取整、概率上下限、额外收获与受伤独立、修为封顶。
2. 新增 0014 迁移、仓储和接口；先实现出发/返程/领取的原子性，再接入公共结算与所有弟子相关写路径。
3. 先用 Worker+D1 测试验证时间/并发/权限，再接前端状态、预览和操作；保留原有探索与挑战规则。
4. 跑全量验证，检查最终 diff，不自动提交/推送。

服务端至少覆盖：炼气拒绝、筑基允许、高境界允许；伤势/守擂/在外/未领取/名额/留守人数限制；跨宗 ID；到期前、恰好到期、超过 12 小时离线、多个弟子不同返程点、时钟回拨；返程前无岗位收益、返程后恢复、余数/容量/事件次数不重复；修为先于返程后静修且不越门槛；晚领取伤势不延期；重复/并发出发、重复/并发领取、和驱逐/派工/服药/布阵/挑战竞态均不半写或重复发奖。旧数据库迁移后不改变现有弟子、资源及历史。

前端至少覆盖：预览真实数值、禁用原因、在外/待领取/已领取状态、倒计时与焦点；完成结果可重新打开查看；移动端无溢出。运行 `npm run test:unit`、`npm run typecheck`、`npm run build`、`git diff --check`；如不能做浏览器视觉检查须在交付时说明。

开发者交付时报告改动文件、0014 迁移/接口、关键取舍、命令实际结果、视口验证与遗留风险。尤其复审分段结算的 12 小时上限、同宗并发名额、跨宗归属、守擂交错和领取幂等性。
