# 灵兽养成与精魄兑换开发计划

> 日期：2026-10-21。状态：待开发；本文不是功能已完成的说明。
>
> 面向实现模型：按本文逐项实施，不自行调整数值、扩展玩法或重新设计界面。本文中的数值和最终兑换规则来自本次用户确认；容量、图鉴、接口等未单独讨论的细节，已在本文固定为实施约定。
>
> 本文覆盖原《灵兽开发计划》中的品质固定、放生无收益、属性成长等相关条款。其他捕捉、战斗和装备规则继续沿用现有代码。特别注意：用户最后确认的是“兑换统一获得 1 级凡品”，此前出现过的“兑换随机品质”方案已废弃。

## 0. 必须先读的约束

1. **样式统一是硬性验收条件：优先复用现有组件、布局和样式；确有缺口时允许新增或调整 CSS。** 新样式必须沿用现有配色变量、字体、尺寸尺度、交互状态与响应式规则，做到与原灵兽苑一致。禁止随意设计另一套视觉风格；具体复用来源与补充规则见第 10 节。
2. 本次只做：灵兽属性与成长调整、御兽精魄、放生收益、品质突破、精魄兑换，以及对应展示和必要测试。
3. 不做批量放生、批量兑换、自动捕捉、连续抽取、兑换保底、兑换随机品质、材料合成、交易、繁殖、新建筑、新美术或新动画。
4. 不修改赌坊“灵兽竞逐”。不要因名称相近改动 `gambling.ts` 的赛跑逻辑。
5. 不修改每日 20 次搜寻、野外物种权重、野外品质概率、区域搜寻费用、收服概率和捕捉状态机。聊天中“每天 15 只灵兽、5 只珍兽”只用于收益估算，**不是新增概率配置，也不是每日保底数量**。
6. 原有灵兽直接按新公式计算，保留 id、物种、品质、等级、装备人、锁定状态。不要清空灵兽、重置等级或补发材料。
7. 数据与费用全部由后端确定。前端只展示后端报价，不能提交所得品质、等级、返还数量、费用或抽取结果。
8. 不重构通用战斗、资源、鉴权、弹窗或结算框架。允许为本功能做最小必要接入。
9. 不修改已发布迁移 `0070`、`0071`；新增下一个未使用的迁移编号。本文写作时下一个编号是 `0072`，实施时先检查是否被占用。
10. 本任务是开发与本地验证；不自行执行远程迁移、生产部署、线上数据修改。

### 2.2 成长公式

- 等级范围仍为 1～20，升级必定成功。
- 最终单项属性：`floor(基础属性 × 品质属性倍率 × (1 + 0.06 × (等级 - 1)))`。
- 技能数值系数：`品质技能倍率 × (1 + 0.03 × (等级 - 1))`。
- 属性仅在最终一步向下取整，不逐级累计加点。等级或品质变化后统一重新计算。
- 保留现有技能的基础数值与安全上限。触发概率、每场次数、35% 门槛、免疫、首击必暴等开关机制不随品质/等级放大。
- 沿用现有技能展示精度，使用 `beastSkillText`，前端不另算技能。

| 品质 | 枚举 | 属性倍率 | 技能倍率 | 野外品质权重 |
|---|---|---:|---:|---:|
| 凡品 | `common` | 1.0 | 1.0 | 70 |
| 灵品 | `spirit` | 1.2 | 1.1 | 24 |
| 宝品 | `treasure` | 1.4 | 1.2 | 5 |
| 仙品 | `immortal` | 1.6 | 1.3 | 1 |

普通等级升级仍消耗 `10 × 当前等级 × 档次系数` 灵石和 `8 × 当前等级 × 档次系数` 灵气；档次系数为灵兽 1、珍兽 2、神兽 3，不消耗精魄。

应当通过的固定示例：

| 档次 | 20 级凡品主 / 副属性 | 20 级仙品主 / 副属性 |
|---|---|---|
| 灵兽 | 14 / 4 | 23 / 6 |
| 珍兽 | 21 / 6 | 34 / 10 |
| 神兽 | 29 / 8 | 47 / 13 |

### 2.3 不连带增强野生目标

当前 `startBeastCapture` 使用 `beastAttributes({ quality:'common', level:1 })` 生成野生目标属性。直接修改基础定义会把野生目标一起增强，必须在调整前拆开。

- 新增明确的野生属性来源，例如 `wildBeastAttributes(speciesId)`，固定使用原主 / 副属性：灵兽 6 / 2，珍兽 9 / 3，神兽 12 / 4；属性方向与上表对应。
- 野生目标的 `attack:40+...`、`defense:35+...`、`speed:40+...`、`luck:35+...`、`physique:40+...`、区域强度 35 / 95 / 180 及档次强度系数继续沿用。
- 野生技能仍按 1 级凡品，不使用本次随机品质，也不读取收藏灵兽的培养进度。
- 野生品质仍只决定捕获结果，不能通过目标血量反推品质。
- 已保存的捕捉会话使用原 `data` 快照继续结算；不得在读取/操作时重建战斗双方。
- 玩家携带的收藏灵兽按新公式生效，这是培养增强的正常结果。

## 3. 御兽精魄：存储、单位与展示数据

### 3.1 资源定义

实施约定：复用 `resource_balances`，不新建第二套材料钱包。

| 字段 | 固定值 |
|---|---|
| id | `beastEssence` |
| 名称 | 御兽精魄 |
| 初始数量 | 0 |
| 自然产量 | 0 |
| 配置可见性 | `public` |
| 基础容量 | 999999 个，即配置 `capacity: '999999000'` |
| 单位 | 1 个 = `MIN_UNITS_PER_DISPLAY_UNIT` = 1000 最小单位 |
| 入账来源 | 本次仅放生 |
| 消耗用途 | 品质突破、灵兽兑换 |

- 不加入岗位产出、离线奖励、功勋商店、坊市交易、拍卖行资源池或赌坊可下注白名单。
- 容量沿用现有 `effectiveCapacity` 规则；前端无需单独展示精魄库容。
- 放生前必须检查完整奖励是否能入账。达到容量或金额上限时，整笔拒绝，保留灵兽；禁止删兽后截断奖励。
- 新增资源配置后，按仓库机制更新 `GAME_CONFIG_VERSION`、`GAME_CONFIG_PAYLOAD_HASH` 和 seed 的配置行。当前为 v12，未有其他变更时用 v13.0.0。hash 必须计算，禁止手填猜测或绕过校验。

### 3.2 单位不得混用

本文所有费用表是“显示单位”；数据库和资源接口统一使用最小单位。

示例：随机神兽 50 精魄应扣 `50000`；指定神兽 300 应扣 `300000`；凡品神兽放生 10 应加 `10000`。

- 纯规则常量使用最小单位，并在名字/注释中注明，如 `BEAST_EXCHANGE_COST_UNITS`。
- 复用 contracts 的单位常量，不在各文件散写 1000。
- 新增资源费用/奖励 DTO 使用十进制字符串；比较前按现有安全金额工具转为 number。禁止 NaN、小数、负余额、超过 `MAX_SAFE_AMOUNT`。
- 前端使用现有 `formatAmount` 展示，禁止再次乘除后传给它；客户端不得提交计算后的费用。
- 精魄当前只按整数个获得/消费，余额和 delta 应为 1000 的整数倍，`remainder` 为 0。

### 3.3 初始与迁移

- 新迁移为每个已有宗门补 `beastEssence` 余额行：0 余额、0 余数；通过 `WHERE NOT EXISTS` 防止覆盖已有值。
- 新宗门通过现有 `createSect` 遍历配置自动创建该资源行。
- 不给已有宗门发初始精魄，不补偿历史放生，不改已有灵兽数据。
- 资源行是写命令的必需条件：缺行时不能让 `UPDATE` 影响 0 行却删除灵兽或发出兑换物。必须报初始化异常并保持业务数据不变；不要临时新增不受快照守卫覆盖的余额行。
- 当前命令表需新增可空 `receipt_json TEXT`，用途见第 8 节；旧记录保持 NULL。

## 4. 放生收益

| 当前品质 | 灵兽 | 珍兽 | 神兽 |
|---|---:|---:|---:|
| 凡品 | 1 | 3 | 10 |
| 灵品 | 3 | 9 | 30 |
| 宝品 | 8 | 24 | 80 |
| 仙品 | 20 | 60 | 200 |

行为顺序：

1. 严格校验输入、鉴权、根据当前用户确定宗门。
2. 检查命令幂等，再按 `id + sect_id` 读取灵兽并核对 version。
3. 已锁定或已装备一律拒绝，不自动卸下、不自动解锁。
4. 防御性检查：若该灵兽 id 仍出现在本宗有效 active 捕捉的玩家携带快照中，拒绝放生，即便库内装备关系异常为空；忽略已结束或过期快照。快照字段与旧会话兼容方式见下文。
5. 以后端读取的物种档次、当前品质计算奖励。等级不影响收益，培养投入不另退。
6. 检查精魄余额行存在、完整奖励入账容量和安全金额。
7. 在同一个受保护 batch 内：删除灵兽、增加精魄、写命令回执。必须全成或全败。
8. 返回新的宗门状态、灵兽面板和实际奖励回执。

图鉴历史记录保留。刷新、重复点击、并发放生同一只、响应丢失后原命令重试，不能重复加精魄。请求时携带的旧品质、旧 version 不得用于结算。

现有 `CaptureData.player.beast` 是 `BeastMods`，**没有灵兽 id**，不能直接假定其中存在 id，也不能按同名物种误拦其他个体。为新会话增加 `carriedBeastId?: string | null`：开始捕捉时从 `readBeast(m)?.id` 保存；旧JSON缺字段时，检查该会话弟子现有 `beast_json` 中的 id 作为兼容回退。只读取身份，不重算任何战斗数值。不要把“旧快照没有此字段”判成会话损坏或重开遭遇。

## 5. 品质突破

品质按 `common → spirit → treasure → immortal` 逐级提升，成功率 100%，不能跳级。

| 档次 | 品质突破 | 精魄 | 灵石 | 灵气 |
|---|---|---:|---:|---:|
| 灵兽 | 凡 → 灵 | 4 | 100 | 80 |
| 灵兽 | 灵 → 宝 | 10 | 300 | 240 |
| 灵兽 | 宝 → 仙 | 25 | 800 | 640 |
| 珍兽 | 凡 → 灵 | 12 | 200 | 160 |
| 珍兽 | 灵 → 宝 | 30 | 600 | 480 |
| 珍兽 | 宝 → 仙 | 75 | 1600 | 1280 |
| 神兽 | 凡 → 灵 | 40 | 300 | 240 |
| 神兽 | 灵 → 宝 | 100 | 900 | 720 |
| 神兽 | 宝 → 仙 | 250 | 2400 | 1920 |

累计到仙品：灵兽 39 精魄 / 1200 灵石 / 960 灵气；珍兽 117 / 2400 / 1920；神兽 390 / 3600 / 2880。

### 5.1 状态边界

- 仙品不能继续突破，后端拒绝且不扣费；20 级但未仙品仍可突破。
- 品质突破不要求额外等级门槛，也不增设额外宗门门槛；宗门 3 级开放玩法后，已拥有灵兽即可培养。
- 保留 id、物种、等级、五行、装备人、锁定状态。锁定只防放生，允许升级、突破和装备。
- 占用限制与现有等级升级一致：随行弟子正在捕捉或在进行中的普通秘境队伍内时拒绝；历练、执事、坐镇、疗伤状态不额外禁止品质培养。
- 不把限制写成“所有忙碌弟子都不能突破”，也不把升级操作原有的例外收紧。
- 培养不改写已经形成的战斗、历练、大比等快照；读取实时状态的后续战斗自然使用新数据。

### 5.2 提交流程

1. 复用管理接口，新增动作 `quality-breakthrough`，不要混用弟子境界突破接口。
2. 检查归属、version、当前品质和上述占用条件。
3. 用纯规则函数确定下一品质、三种费用、下一级属性/技能预览。
4. 三种资源任一不足，整笔失败，不改变品质、不部分扣费。
5. 同批扣费、更新 `spirit_beasts.quality`、`version + 1`、`updated_at`。
6. 若已装备，必须同批调用现有 `refreshCache` 更新 `disciples.beast_json`；不要只改灵兽表导致实际战斗仍按旧品质。
7. 同批更新图鉴最高品质并写命令回执；返回当前 state 和 beasts。
8. 返回的弟子属性、面板战力、技能文本必须与新缓存一致。不要额外写 `gear_power_bp` 或发明灵兽战力百分比。

## 6. 精魄兑换

### 6.1 固定价格与产出

| 档次 | 枚举 | 随机兑换 | 指定兑换 | 宗门门槛 |
|---|---|---:|---:|---:|
| 灵兽 | `spirit` | 6 | 36 | 3 |
| 珍兽 | `rare` | 18 | 54 | 5 |
| 神兽 | `divine` | 50 | 300 | 7 |

所有产出固定为：`quality:'common'`、`level:1`、`locked:0`、`disciple_id:NULL`、初始 version 0、新 UUID。

- 随机：先选档次，在该档次物种中等概率抽一只。池大小为 5 / 2 / 5。
- 指定：选择该档次中的合法物种，直接获得该物种。
- 均允许获得重复物种；不限制“必须已见过”，不做唯一性去重或换一种保底。
- 不调用 `encounterSpecies`，它包含野外档次权重和幸运修正；不调用 `encounterQuality`。
- 一次请求只兑换一只，没有 quantity 参数，不提供连抽和批量。
- 仅消耗精魄，不额外消耗灵石、灵气、搜寻次数，也不要求选择弟子。
- 不生成捕捉会话，不占用弟子，不改变捕捉每日计数。

### 6.2 图鉴口径

实施约定：现有 `caught_count` 扩展为“累计获得数量”，野外捕获与兑换各 +1；前端图鉴将“已收服 ×N”改为“已获得 ×N”。不新增第二套重复统计。

- `seen_count` 仍只记录野外遭遇，兑换不增加该计数。
- 兑换获得此前未见过物种，也应解锁图鉴。判断已获得优先于是否 seen。
- `best_quality` 为曾拥有的最高品质：捕获、兑换、品质突破均只升不降；放生不降低。
- `best_quality` 更新用单条 SQL 的品质等级比较或等价守卫避免并发降级；不要用无守卫的旧值覆盖新值。
- 不追溯扫描历史记录，不修改历史数量。新命令按上述口径开始计数。

## 7. 容量预留与并发（必须完整实现）

宗门灵兽容量仍为 60。有效捕捉为 `status='active' AND expires_at > now`，为它预留 1 个位置。

```text
owned = 当前宗门 spirit_beasts 总行数
reserved = 当前宗门存在有效捕捉 ? 1 : 0
兑换允许条件：owned + reserved + 1 <= 60
开始新捕捉：不存在有效捕捉，且 owned + 1 <= 60
当前捕捉收服成功：owned + 1 <= 60（消耗自己已预留的位置）
```

| 当前拥有 | 有效捕捉 | 兑换结果 |
|---:|---|---|
| 59 | 无 | 允许一只 |
| 59 | 有 | 拒绝，为捕捉留最后一格 |
| 58 | 有 | 允许一只，之后拥有 59 并保留一格 |
| 60 | 无 / 有 | 拒绝 |
| 59 | 仅过期记录 | 允许一只 |

- 后端必须在与写入同一批次的守卫中核验容量和有效捕捉；前端禁用按钮不能代替。
- 开始捕捉与兑换并发时，复用/补充双方现有守卫，确保不能同时抢走最后一个位置。
- 两个不同 commandId 并发兑换最后一格只能成功一个，另一个不扣费。
- 捕获成功与兑换并发同样不能超容量，也不能先扣费后报“无法存入”。
- 面板返回 `reservedSlots`（0 或 1）和 `availableSlots=max(0,capacity-items.length-reservedSlots)` 供前端禁用及说明使用；服务端写入仍现查现验。
- 不要仅用 `panel.active` 判断：容量守卫必须查询该宗门所有有效 active 行，避免依赖“最近一条”假设。
- 过期活动不预留，不因兑换去重建或删除捕捉记录。

## 8. 原子性、幂等和回执

### 8.1 复用现有机制

- 继续使用 `draftFor`、`SectDraft.requireResource/addResource`、`commit({extraGuards})`、`mutation_guards` 和 `beast_commands`。
- 资源余额、宗门状态、相关弟子缓存、灵兽 version、容量等检查与写入放在同一 `db.batch` 中。D1 和 Node SQLite 适配器都必须支持这条路径。
- 禁止先扣资源 `await run()`，再单独插入灵兽；禁止先删除灵兽再单独入账。
- 所有灵兽读写限定本宗门；用户和宗门 id 必须从登录状态得出。
- 任意 SQL/守卫失败，资源、灵兽、图鉴、缓存、回执全回滚。

### 8.2 命令约束

- 所有写请求带 UUID `commandId`。管理请求继续带非负整数 version。
- 幂等键仍为 `(sect_id, command_id)`，同一宗门内跨操作共用；fingerprint 必须包含操作类别及有效业务参数。不要让同一个 key 在“放生”和“兑换”间被误认作重放。
- 同 key 同参数：不再次扣费、不再次抽随机物种、不重复加材料、不重复计图鉴，返回原业务回执和当前 state/beasts。
- 同 key 不同参数或不同操作：返回 `VALIDATION_ERROR`，不能执行第二次。
- 保留旧动作现有 fingerprint 编码或提供明确兼容读取，不得全局更换编码后把全部旧幂等记录误判为参数冲突。旧版已成功的放生命令重试只返回当前状态，**不追发精魄、不再次放生**；NULL回执不是补执行的理由。
- 不同 key 但旧 version：拒绝，不能拿旧状态重复突破/放生。
- 并发同 key：数据库唯一约束保证只有一笔提交；失败方确认已存在同 fingerprint 后按重放返回。
- 现有记录清理窗口为 7 天，本期保持该窗口。前端未决请求重试不跨该窗口；本期不新增永久账本。不得把幂等描述成永久有效。

### 8.3 为什么要保存回执

当前命令表只有 fingerprint/session_id，重放只能返回最新面板。随机兑换后若灵兽已经升级或放生，仅从最新列表可能无法复原原结果，因此新增 `receipt_json`。

回执保存不可变事实，至少包括：

```ts
interface BeastCommandReceipt {
  commandId: string;
  kind: 'release' | 'quality-breakthrough' | 'exchange';
  beast: BeastIdentity; // 当次结果的快照；放生为被放生对象
  previousQuality: BeastQuality | null; // 突破时为原品质，其他为 null
  // delta 为 { direction:'credit'|'debit', amount:string }，不使用带负号金额字符串
  resourceChanges: Partial<Record<'beastEssence'|'spiritStone'|'spiritualEnergy', {
    direction: 'credit' | 'debit'; amount: string;
  }>>;
}
```

- 回执与业务写入同批保存，不另写一次提交。
- `beast` 为原始快照，不依赖其 id 对应的当前行继续存在；重放时不重新算当下费用。
- 管理接口原来的 equip/unequip/upgrade/lock 不要求补历史回执。兼容旧命令 `receipt_json=NULL`，重放不得补执行。
- 新财务操作的成功响应含 receipt；无法完整恢复的新操作不能用“再执行一次”补回执。

### 8.4 前端请求未决状态

- 一次确认生成一个 commandId；pending 时禁用再次操作并接入现有 loading。
- 连接中断、非 JSON/5xx 等无法确定是否提交的失败，保留原 payload 和 commandId，提供“重试原操作”，不可自动生成新 id 再抽一次。
- 对确定业务拒绝（资源不足、旧 version 等），刷新后可作为新操作重新确认并生成新 id。
- 未决操作的参数不允许悄悄改变后复用旧 id；切换目标需先确认/恢复原结果。
- 失败后刷新面板与宗门状态，不能只刷新 beasts 导致首页精魄仍旧。
- 本期不加跨浏览器持久化队列。刷新页面后的余额/灵兽来自服务器，不自动重发上次写请求。

## 9. API 和共享契约

### 9.1 面板与管理返回

`GET /api/v1/game/spirit-beasts` 扩展为 `{ state, beasts }`，保留 beasts 字段兼容现有调用者。写接口返回 `{ state, beasts, receipt }`，普通旧管理动作可返回 `receipt:null`。

- 御兽精魄余额只从 `state.resources[id='beastEssence'].balance` 读取，不在面板另存第二份余额。
- 前端成功后先使用同一响应更新 state 和 panel，再显示回执。
- 首次加载和错误恢复都要同步 state。`syncSect()` 已存在，可用于额外恢复；不要直接修改 props 或猜测余额。

`SpiritBeastView` 增加以下只读数据，具体接口名按此使用，避免各端重复计算：

```ts
releaseReward: { beastEssence: string };
qualityBreakthrough: null | {
  nextQuality: BeastQuality;
  nextQualityName: string;
  cost: { beastEssence: string; spiritStone: string; spiritualEnergy: string };
  attrs: BeastAttrs;       // 下一品质、当前等级的最终属性
  skillText: string;
  blockedReason: string | null;
};
upgradePreview: null | {
  level: number; attrs: BeastAttrs; skillText: string;
};
```

- 仙品 `qualityBreakthrough:null`；20 级 `upgradePreview:null`。满级不能误禁用品质突破。
- blockedReason 显示活动限制等原因；资源不足按同一响应余额/费用判断，后端执行时再验。
- 增加面板 `exchangeOffers`，每档包含 tier、tierName、requiredSectLevel、unlocked、randomCost、specificCost、speciesIds；费用为最小单位字符串。
- 增加第 7 节 reservedSlots / availableSlots，前端不另写容量公式。
- 前端不能硬编码另一份价格、返还表或物种池；来自面板/灵兽 view。

### 9.2 品质突破请求

复用 `POST /api/v1/game/spirit-beasts/manage`：

```json
{
  "beastId": "灵兽UUID",
  "version": 3,
  "commandId": "本次命令UUID",
  "action": "quality-breakthrough"
}
```

强化 schema：用严格的判别联合约束不同 action。equip 必须 discipleId；lock 必须 locked；其他动作拒绝这些无关字段。不能只扩 enum 却让任意参数组合穿过。

### 9.3 兑换请求

新增 `POST /api/v1/game/spirit-beasts/exchange`：

```ts
type BeastExchangeInput =
  | { mode:'random'; tier:BeastTier; commandId:string }
  | { mode:'specific'; tier:BeastTier; speciesId:string; commandId:string };
```

- 两个分支均用 `z.strictObject`，mode 为判别字段；random 带 speciesId 也应拒绝。
- specific 的物种必须存在且档次与 tier 一致，门槛按服务端物种档次和报价表验证。
- 请求里的 quality、level、cost、quantity、resourceId、discipleId 等未声明字段直接 400。
- 所有路由沿用现有鉴权、Origin、CSRF 与错误响应封装，不提供测试后门或裸 SQL 入口。
- 随机函数可在服务函数参数中注入，默认 Math.random；HTTP 客户端不能指定 seed/random。
- 前端补 `exchangeSpiritBeast` API 包装，扩展管理动作联合、GET 返回类型及回执类型。

### 10.1 样式边界

**允许新增 CSS，但必须先检查能否复用。验收看视觉一致性、必要性与影响范围，不以 CSS 行数为零作为要求。** 新增交互优先在 `BeastGardenDialog.vue` 内完成，使现有 scoped 样式直接可用；确需拆组件时，也可以增加本组件的 scoped 样式。
