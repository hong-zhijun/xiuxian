# 宗门挑战优化开发计划

## 1. 文档目的

本文档用于指导后续开发、测试和验收宗门挑战优化。实现者应先阅读现有挑战代码和迁移，再按本文档实施；不应只在前端改文案或只把限制常量从 1 改成 3。

本次优化的核心是：

- 玩家每个 UTC+8 自然日可主动挑战 3 次。
- 胜利奖励根据攻守双方宗门等级差动态计算。
- 未设置有效守擂阵容的宗门也可以被挑战，系统为它随机生成临时守擂阵容。
- 同一攻方每天对同一宗门最多发起 1 次挑战。
- 限次、奖励和挑战记录在并发请求下也必须保持一致。

## 2. 范围与非目标

### 2.1 本次范围

- 数据库迁移、每日次数状态和挑战历史快照。
- 奖励档位计算、自动守擂选人、重复挑战校验和并发保护。
- 公开宗门详情中的挑战预览。
- 挑战对话框、结果、演武录和排行榜提示的同步更新。
- 服务端、迁移和前后端契约的测试。

### 2.2 本次不做

- 不改 3v3 顺序对战、先胜 2 局的战斗规则。
- 不改战力公式、战斗浮动、平局判定或攻方选人方式。
- 不为守方发放奖励，不消耗守方的主动挑战次数。
- 不增加挑战门票、弟子伤势、排位分或连胜奖励。
- 不重构与挑战无关的模块。

## 3. 已确认的产品规则

### 3.1 每日次数

1. 以 UTC+8 的 00:00 为日切换点，每天可主动挑战 3 次。
2. 只要请求通过全部前置校验并真正产生了一场战斗，就消耗 1 次；胜利、失败和零奖励胜利都一样消耗。
3. 目标不存在、挑战自己、次数已用完、当日已挑战过该目标、攻方阵容无效、目标弟子不足等前置校验失败，都不消耗次数。
4. 被动守擂不消耗守方次数，守方无论胜负都不获得本系统奖励。
5. 同一攻方在同一天内对同一守方最多发起 1 场。重复目标要在战斗前直接拒绝，且不多扣次数。

### 3.2 等级差和胜利奖励

统一定义：

`levelDifference = 守方宗门等级 - 攻方宗门等级`

仅攻方胜利时发放奖励：

| 等级差 | 语义 | 声望 | 灵石展示值 | 灵石存储值 |
| --- | --- | ---: | ---: | ---: |
| `<= -3` | 守方低至少 3 级 | 0 | 0 | 0 |
| `-2` | 守方低 2 级 | 5 | 50 | 50000 |
| `-1` | 守方低 1 级 | 8 | 75 | 75000 |
| `0` | 同级 | 10 | 100 | 100000 |
| `+1` | 守方高 1 级 | 13 | 125 | 125000 |
| `+2` | 守方高 2 级 | 15 | 150 | 150000 |
| `>= +3` | 守方高至少 3 级 | 20 | 200 | 200000 |

补充规则：

- 失败的声望和灵石奖励始终是 0。
- 跨级奖励在 `>= +3` 封顶，不再随等级差继续增加。
- `<= -3` 的目标仍然可以挑战，但必须明确提示“胜利也无奖励，且会消耗 1 次”。
- 奖励以战斗开始时记录的攻守双方宗门等级为准，不从之后的宗门状态反推。

### 3.3 守擂阵容

1. 守方已设置有效阵容时，使用该阵容并保留玩家设置的顺序。
2. “有效守擂阵容”指恰好 3 个不重复的弟子 ID，且这 3 名弟子在挑战发生时仍然都属于守方。
3. 守方没有有效阵容，但当前至少有 3 名弟子时，系统从当前全部弟子中等概率、不重复地随机抽取 3 名，并随机决定对战顺序。
4. 自动守擂可选中受伤弟子，与当前“预设守擂不检查伤势”的规则保持一致。
5. 守方当前弟子少于 3 名时不能被挑战，拒绝后不消耗攻方次数。
6. 旧的阵容数据若包含重复、已不属于该宗门的弟子或格式无效，视为无有效阵容；弟子足够时改用自动守擂，而不是用 0 战力占位。
7. 临时阵容一旦选定，必须在当场战斗、返回结果和历史记录中使用同一份快照。
8. 战斗前只告知攻方“对方将使用临时自动守擂”，不暴露本场随机选中的 3 人和出战顺序。

## 4. 数据设计

### 4.1 新迁移

新建 `migrations/0012_challenge_rewards.sql`，不回改已经发布的 `0009_challenge_system.sql`。

`sects` 增加：

| 字段 | 类型 | 要求 |
| --- | --- | --- |
| `challenge_date_key` | `TEXT NOT NULL DEFAULT ''` | UTC+8 日期键，格式 `YYYY-MM-DD` |
| `challenge_count` | `INTEGER NOT NULL DEFAULT 0` | 对应日期已受理场次，必须 `>= 0` |

`challenge_log` 增加以下可空快照字段，保证旧记录仍能读取：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `attacker_level` | `INTEGER` | 开战时攻方宗门等级 |
| `defender_level` | `INTEGER` | 开战时守方宗门等级 |
| `reward_tier` | `TEXT` | 开战时匹配到的奖励档位 |
| `defense_mode` | `TEXT` | `configured` 或 `automatic` |
| `challenge_date_key` | `TEXT` | 本场对应的 UTC+8 日期键 |

索引：

- 为 `(attacker_sect_id, defender_sect_id, challenge_date_key)` 建立唯一部分索引，仅约束 `challenge_date_key IS NOT NULL` 的新记录，从数据库层保证同一攻方当日不能重复挑战同一目标。
- 按查询计划补充 `(attacker_sect_id, challenge_date_key)` 普通索引；保留现有按 `created_at` 的索引，用于兼容旧记录和历史查询。

### 4.2 每日计数的兼容逻辑

不再把“先查日志数量，再写日志”作为唯一限次手段，因为两个并发请求可能读到相同数量。

计数状态的口径：

- `challenge_date_key === dateKeyUtc8(now)` 时，当日使用量取 `challenge_count`。
- 日期键不一致时，将当日有效使用量视为 0。为避免发布当天忽略迁移前已发生的挑战，首次切换可用现有 `challenge_log.created_at >= dayStartMs(now)` 查询进行兼容核对，并在下一场成功受理的挑战中一次性写回新日期键和新计数。
- 展示值始终限制在 `0..3`，`remaining = max(0, 3 - usedToday)`。数据异常不应让前端显示负数。

### 4.3 档位标识

奖励定义必须放在一个单一、可测试的后端表或纯函数中，不要在 service、前端和文案中各写一套分支。建议使用稳定标识：

- `lower_3_plus_no_reward`
- `lower_2`
- `lower_1`
- `equal`
- `higher_1`
- `higher_2`
- `higher_3_plus`

标识一旦写入历史，后续不应随意改名。前端展示的中文标签可单独转换。

## 5. 后端设计

### 5.1 建议的纯逻辑拆分

为避免 `service.ts` 继续膨胀，可新建一个挑战领域模块，例如 `apps/server/src/modules/game/challenge.ts`，放置不访问数据库的定义和函数：

- `CHALLENGE_DAILY_LIMIT = 3`。
- 奖励档位表及“根据等级差返回档位”的纯函数。
- `DefenseMode`、`RewardTier`等类型。
- 无改写地打乱候选弟子并取 3 人的函数。函数应允许测试注入确定性随机源，生产环境再使用项目现有随机方式。

如果项目已有更合适的相邻模块，可遵循现有组织方式，但奖励表必须保持单一事实来源。

### 5.2 Repository 能力

在 `apps/server/src/modules/game/repository.ts` 中扩展：

- `SectRow` 和所有查询宗门的 `SELECT` 包含新的日期键与计数字段。
- `ChallengeLogRow` 包含新的可空快照字段。
- 查询当日是否已挑战指定宗门，查询时要兼容旧记录的 `created_at` 日窗口。
- 原子更新 `challenge_date_key` 和 `challenge_count`的 statement。
- 写挑战日志时同时写入等级、档位、守擂方式和日期键快照。
- 参考炼丹已有的 `mutation_guards` 方式，增加挑战快照守卫 statement和对应清理 statement。

### 5.3 公开宗门挑战预览

现有 `GET /api/v1/game/sect/:sectId` 虽然要求登录，但 service 只接收目标宗门 ID。调整 route，将当前 `userId` 和 `now` 传入 `getPublicSect`，使返回值可以相对当前玩家计算。

`PublicSectView` 保留原有安全字段，新增一个 `challenge` 预览对象：

| 字段 | 说明 |
| --- | --- |
| `canChallenge` | 当前是否可发起挑战 |
| `blockedReason` | 不可挑战的稳定原因码，可为 `self`、`daily_limit`、`already_challenged_today`、`defender_insufficient`或 `null` |
| `defenseMode` | `configured`、`automatic` 或因弟子不足而为 `null` |
| `dailyLimit` | 固定为 3 |
| `usedToday` | 当日已受理场次 |
| `remaining` | 当日剩余场次 |
| `alreadyChallengedToday` | 今日是否已挑战该目标 |
| `levelDifference` | 守方等级减攻方等级 |
| `rewardPreview` | 确切的档位、声望和灵石奖励，表示“若胜利”可得 |

原有 `hasDefenseLineup` 可保留以减少不必要的契约破坏，但它只表示“有有效的手动守擂阵容”，前端不得再用它作为能否挑战的唯一条件。

公开详情仍不返回本场自动阵容的人选或顺序。自动阵容只在 POST 挑战真正受理时生成。

### 5.4 主状态契约

`SectStateView` 新增：

```text
challenge: {
  dailyLimit: 3,
  usedToday: number,
  remaining: number
}
```

所有会返回宗门主状态的流程都应得到相同口径的当日次数，不只是挑战接口。日期过期时可在内存视图中归零，不需要为了读取页面而单独写库。

### 5.5 挑战结果和历史契约

`ChallengeResultView` 新增：

- `attackerLevel`
- `defenderLevel`
- `levelDifference`
- `rewardTier`
- `defenseMode`

现有 `reputationGained` 和 `spiritStoneGained` 仍是本场实际发放值，前端不应根据预览再自行计算。失败或零奖励胜利时这两个值为 0。

`ChallengeHistoryEntryView` 新增同类快照字段，但等级、档位和守擂方式允许为 `null`，以兼容迁移前的旧记录。旧记录照常显示胜负、比分和实际奖励，不伪造等级差或奖励档位。

### 5.6 `challengeSect` 处理顺序

建议严格按以下顺序执行：

1. 加载并结算攻方宗门草稿状态。
2. 校验目标存在，且不是攻方自己。
3. 按 UTC+8 归一化攻方当日计数，校验小于 3。
4. 查询并拒绝当日已挑战过的目标。
5. 校验攻方恰好选择 3 名不重复、属于自己且未受伤的弟子。
6. 一次性加载守方当前全部弟子。
7. 校验手动守擂阵容；有效则使用并保持顺序，无效则尝试生成临时自动阵容。
8. 守方弟子少于 3 名则拒绝，不消耗次数。
9. 快照攻守双方等级，计算等级差、奖励档位和胜利预期奖励。
10. 使用已确定的双方阵容解算战斗。
11. 胜利时按档位发奖，失败时发放 0；`<= -3` 的胜利也发放 0。
12. 在同一个受保护的 D1 batch 中更新攻方当日计数、发放奖励、写入挑战日志和完成原有结算。
13. 提交成功后，返回含最新剩余次数的 state 和完整战斗结果。

“受理了一场战斗”的边界是整个 batch 成功。batch 失败时，次数、奖励和日志必须全部回滚。

### 5.7 并发与幂等保护

仅靠 service 中的先查后写不够。实现时必须同时使用：

- 类似炼丹的 `mutation_guards` 快照校验，校验攻方的宗门等级、声望、结算时间、挑战日期键/计数以及涉及的资源余额仍与读取快照一致。
- 挑战日志唯一索引，阻止同一天并发挑战同一目标。
- 一次且只有一次 batch 提交，不能先扣次数、再单独发奖或写日志。
- 将快照过期和唯一索引冲突转换为项目现有的可理解业务错误，不向前端暴露 SQL 错误。

并发场景的底线：任何情况都不能让成功受理场次超过 3，不能对同一场重复发奖，不能在同一天对同一目标产生两条新记录。

## 6. 前端设计

### 6.1 API 类型

在 `apps/web/src/api/game.ts` 同步后端契约：

- `SectStateView.challenge`。
- `PublicSectView.challenge`。
- 奖励档位、守擂方式、预览奖励类型。
- `ChallengeResultView` 的等级和档位快照。
- `ChallengeHistoryEntryView` 中兼容旧数据的可空快照。

前端不另行维护奖励数值表，直接显示后端 `rewardPreview` 和最终结果数值，避免两端失配。

### 6.2 公开宗门面板

`apps/web/src/components/PublicSectPanel.vue` 调整为：

- 按 `challenge.canChallenge` 控制按钮，不再按 `hasDefenseLineup` 直接屏蔽。
- 显示“今日剩余 X/3 次”。
- 显示等级差和胜利可获得的确切声望/灵石。
- 对 `<= -3` 显示高可见的零奖励警告，但不禁用按钮。
- 显示“已设置守擂阵容”或“将使用临时自动守擂”，不透露临时人选。
- 对次数用完、已挑战过该目标、守方弟子不足等情况显示明确原因。

### 6.3 挑战对话框

`apps/web/src/components/ChallengeDialog.vue` 在选择攻方弟子前后均保留以下信息：

- 今日剩余次数。
- 双方宗门等级与等级差。
- 若胜利的确切奖励。
- 是手动守擂还是临时自动守擂。
- 零奖励或不可挑战的原因。

对 `<= -3` 的目标，在最终挑战按钮附近再次明确提示“胜利无奖励，仍消耗 1 次”，但不额外增加二次弹窗。

成功接口返回后，使用返回的 `state` 更新全局宗门状态，结果页显示实际奖励，不沿用请求前的预览值作为实际发奖结果。

### 6.4 其他页面

- `apps/web/src/components/LeaderboardPanel.vue`：将“每日 1 次”更新为“每日 3 次”，避免继续暗示必须手动布阵才能挑战。
- `apps/web/src/components/ChallengeHistoryPanel.vue`：新记录可显示当时等级差、守擂方式和奖励；旧记录的可空字段不显示占位错误。零奖励胜利应能与失败区分。
- 在现有合适的宗门状态区域显示当日剩余次数；不新造独立卡片或改造整个页面布局。

## 9. 测试计划

### 9.1 迁移和兼容性

- 全新数据库可从 0001 顺利迁移到 0012。
- 旧宗门获得合法默认计数字段。
- 旧 `challenge_log` 记录的新快照字段为 null，仍能出现在演武录。
- 新记录无法在同一日期键下重复同一攻守组合。

### 9.2 奖励边界

至少覆盖等级差 `-10, -3, -2, -1, 0, +1, +2, +3, +10`，验证档位、声望和灵石值全部与表格一致；同时验证任意档位的失败奖励都是 0。

### 9.3 限次和日切换

- 前 3 场合法挑战均可受理，第 4 场拒绝。
- 失败会扣 1 次。
- `<= -3` 的零奖励胜利会扣 1 次。
- 前置校验失败不扣次数。
- UTC+8 23:59:59 与次日 00:00:00 两侧的日期键和剩余次数正确。
- 当日第二次挑战同一目标被拒绝，且不会再扣 1 次。

### 9.4 守擂阵容

- 有效手动阵容优先，且严格保留手动顺序。
- 没有阵容时，自动阵容恰好 3 人、不重复、都属于守方，并且战斗与日志使用同一快照。
- 使用可注入的确定性随机源验证抽取与排序，不写概率性偶发失败的测试。
- 自动阵容可包含受伤弟子。
- 手动阵容含失效 ID、重复 ID 或非本宗弟子时，弟子足够则回退到自动阵容。
- 守方少于 3 名弟子时拒绝，不消耗次数。

### 9.5 结算、日志和契约

- 每个档位的胜利都把正确声望/灵石同步写入账户状态、接口结果和挑战日志。
- `<= -3` 胜利正确记录为胜利，奖励为 0，而不是记录为失败。
- `defenseMode`、双方等级、等级差和档位在预览、结果和日志中口径一致。
- 旧历史数据的 null 快照不导致后端或前端报错。
- 公开详情不暴露自动阵容的当场人选与顺序。

### 9.6 并发与安全

- 同一攻方同时发起多个请求时，成功场次永远不超过 3。
- 同一攻方并发挑战同一目标时，最多只有 1 场成功，也只发放 1 份奖励。
- 快照冲突时整个 batch 回滚，不出现“扣次数但无日志”或“有奖励但无次数”。
- 现有登录、CSRF、Origin 校验和错误映射不被绕过或破坏。

### 9.7 前端验收

- 手动守擂、自动守擂、弟子不足、重复目标、次数用完和零奖励场景都有正确文案与按钮状态。
- 对话框中的剩余次数、等级差和预览奖励与服务端返回一致。
- 挑战完成后，页面立即显示新的剩余次数。
- 常见桌面和移动端宽度下不出现文字、按钮或战报信息重叠。

## 10. 完成标准

开发完成后至少执行：

```bash
npm run test:unit
npm run typecheck
npm run build
git diff --check
```

最终交付必须同时满足：

- 本文档第 3 节的所有产品规则均已实现。
- 数据库、后端契约、前端类型和 UI 没有互相脱节。
- 关键边界和并发场景有自动化测试，不只靠手工点击。
- 旧挑战历史可继续读取。
- 不存在超过 3 次、同日重复目标、重复发奖或部分写入的并发漏洞。
- 除本功能必需改动外，不删除、重写或格式化无关文件。
