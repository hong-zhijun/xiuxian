# V5：挑战系统（3v3 逐对决斗）

目标：把原来的"切磋"改为"挑战"。每个宗门预设 3 人守擂阵容，攻方选 3 人出战，逐对决斗（先赢 2 场胜）。策略性来自排兵布阵的顺序博弈。

前置：V4（弟子属性与天赋）已完成。

---

## 第一节 数据库变更

### 1.1 迁移文件 migrations/0009_challenge_system.sql

```sql
-- 宗门守擂阵容：3 名弟子 id 的 JSON 数组，null 表示未设置（不可被挑战）
ALTER TABLE sects ADD COLUMN defense_lineup TEXT DEFAULT NULL;

-- 挑战记录表（替代旧 sparring_log 的展示用途，旧表保留不删）
CREATE TABLE challenge_log (
  id TEXT PRIMARY KEY,
  attacker_sect_id TEXT NOT NULL REFERENCES sects (id),
  defender_sect_id TEXT NOT NULL REFERENCES sects (id),
  -- 攻方阵容：JSON 数组 [{discipleId, name, power}]
  attacker_lineup TEXT NOT NULL,
  -- 守方阵容：JSON 数组 [{discipleId, name, power}]
  defender_lineup TEXT NOT NULL,
  -- 每轮结果：JSON 数组 [{round, attackerPower, defenderPower, winner: "attacker"|"defender"|"draw"}]
  rounds TEXT NOT NULL,
  -- 最终结果（从攻方视角）：'win' | 'lose'（3v3 不会整体平局；单轮平局算攻方负该轮）
  result TEXT NOT NULL,
  reputation_gained INTEGER NOT NULL DEFAULT 0,
  spirit_stone_gained INTEGER NOT NULL DEFAULT 0,
  created_at INTEGER NOT NULL
);

CREATE INDEX challenge_log_attacker_idx ON challenge_log (attacker_sect_id, created_at);
CREATE INDEX challenge_log_defender_idx ON challenge_log (defender_sect_id, created_at);
```

说明：
- `defense_lineup` 存的是 JSON 数组如 `["disciple-id-1","disciple-id-2","disciple-id-3"]`，顺序就是出战顺序。
- `attacker_lineup` / `defender_lineup` 存快照（含名字和战力），因为弟子可能后续变化或被遣散，记录要能独立展示。
- `rounds` 存每轮详情，前端可以逐轮展示"战报"。
- 旧的 `sparring_log` 表不删、不改，只是新功能不再写入它。

### 2.2 设置守擂阵容 — POST /api/v1/game/set-defense-lineup

请求体：
```ts

```

Zod schema：
```ts

  discipleIds: z.array(z.string().min(1)).length(3),

```

逻辑（在 service.ts）：
1. `draftFor(db, userId, now)` — 结算。
2. 校验 3 个 id 不重复。
3. 校验 3 个弟子都属于该宗门（`draft.discipleById(id)` 逐个检查，不存在抛 NOT_FOUND）。
4. 受伤的弟子**可以**放入守擂阵容（守擂是预设的，不检查伤势）。
5. 写 SQL：`UPDATE sects SET defense_lineup = ? WHERE id = ?`，参数是 `JSON.stringify(discipleIds)`。
6. 内存更新：`draft.sect.defense_lineup = JSON.stringify(discipleIds)`。
7. `draft.commit()` → 返回 `{ state }`。

新增 statement 构造器：
```ts
export function updateSectDefenseLineupStatement(
  sectId: string,
  lineupJson: string,
): ParameterizedQuery {
  return {
    sql: 'UPDATE sects SET defense_lineup = ? WHERE id = ?',
    params: [lineupJson, sectId],
  };
}
```

### 3.2 战斗流程

逐对决斗，共 3 轮，先赢 2 轮者胜：

```ts
interface RoundResult {
  round: number;           // 1, 2, 3
  attackerPower: number;   // 浮动后战力
  defenderPower: number;
  winner: 'attacker' | 'defender';  // 单轮平局（概率极低）算 defender 胜
}
```

每轮：
1. 取攻方阵容第 N 个弟子 vs 守方阵容第 N 个弟子。
2. 各自算战力（`discipleCombatPower`），然后 ±15% 随机浮动（沿用现有的 `fluctuatedPower`）。
3. 高者胜该轮。平局算守方胜（守方优势：你预设了阵容，本身就有信息劣势）。
4. 攻方赢满 2 轮 → 整场胜；守方赢满 2 轮 → 整场负。**第 3 轮只在 1:1 时打**。

```ts
function resolveChallenge(
  attackerMembers: { discipleId: string; name: string; power: number }[],
  defenderMembers: { discipleId: string; name: string; power: number }[],
): { rounds: RoundResult[]; result: 'win' | 'lose' } {
  const rounds: RoundResult[] = [];
  let attackerWins = 0;
  let defenderWins = 0;

  for (let i = 0; i < 3; i++) {
    if (attackerWins >= 2 || defenderWins >= 2) break;

    const aPower = fluctuatedPower(attackerMembers[i].power);
    const dPower = fluctuatedPower(defenderMembers[i].power);
    const winner = aPower > dPower ? 'attacker' : 'defender';

    rounds.push({
      round: i + 1,
      attackerPower: aPower,
      defenderPower: dPower,
      winner,
    });

    if (winner === 'attacker') attackerWins++;
    else defenderWins++;
  }

  return { rounds, result: attackerWins >= 2 ? 'win' : 'lose' };
}
```

### 3.3 POST /api/v1/game/challenge

请求体：
```ts
{
  targetSectId: string,
  discipleIds: [string, string, string]  // 攻方出战阵容，顺序就是对阵顺序
}
```

Zod schema：
```ts
export const challengeRequestSchema = z.object({
  targetSectId: z.string().min(1),
  discipleIds: z.array(z.string().min(1)).length(3),
});
```

逻辑（service.ts `challengeSect` 函数）：
1. `draftFor(db, userId, now)` — 结算。
2. 校验目标宗门存在、不是自己。
3. **每日限次**：查 `challenge_log` 表，`attacker_sect_id = mySectId AND created_at >= dayStartMs` 的数量 >= 1 → 抛 DAILY_LIMIT。
4. 校验目标宗门 `defense_lineup IS NOT NULL`（不为 null），否则抛 INVALID_STATUS（"对方尚未设置守擂阵容"）。
5. 校验攻方 3 个弟子 id 不重复、都属于自己、都未受伤。
6. 解析守方 `defense_lineup` JSON → 3 个弟子 id。
7. 查守方弟子详情（`DiscipleRepository.findById`）。如果守方某弟子已不存在（被遣散等未来功能），该位置战力视为 0。
8. 构造双方阵容，调用 `resolveChallenge`。
9. 胜利时：声望 +10，灵石 +100（展示单位）。
10. 写 `challenge_log`。
11. `draft.commit()` → 返回 `{ state, result: ChallengeResultView }`。

### 3.5 ChallengeRepository

```ts
export class ChallengeRepository extends ParamRepository {
  async countTodayByAttacker(sectId: string, dayStartMs: number): Promise<number> {
    const row = await this.one<{ total: number }>({
      sql: 'SELECT COUNT(*) AS total FROM challenge_log WHERE attacker_sect_id = ? AND created_at >= ?',
      params: [sectId, dayStartMs],
    });
    return Number(row?.total ?? 0);
  }

  async findBySectId(sectId: string, limit: number): Promise<ChallengeLogRow[]> {
    return this.all<ChallengeLogRow>({
      sql: `SELECT * FROM challenge_log
            WHERE attacker_sect_id = ? OR defender_sect_id = ?
            ORDER BY created_at DESC LIMIT ?`,
      params: [sectId, sectId, limit],
    });
  }

  async statsBySectId(sectId: string): Promise<{ wins: number; losses: number }> {
    // 攻方视角的胜负（被挑战时从守方视角翻转）
    const atkRows = await this.all<{ result: string; cnt: number }>({
      sql: 'SELECT result, COUNT(*) AS cnt FROM challenge_log WHERE attacker_sect_id = ? GROUP BY result',
      params: [sectId],
    });
    const defRows = await this.all<{ result: string; cnt: number }>({
      sql: 'SELECT result, COUNT(*) AS cnt FROM challenge_log WHERE defender_sect_id = ? GROUP BY result',
      params: [sectId],
    });
    let wins = 0, losses = 0;
    for (const r of atkRows) {
      if (r.result === 'win') wins += Number(r.cnt);
      else losses += Number(r.cnt);
    }
    for (const r of defRows) {
      // 守方：攻方 win = 我方 lose，攻方 lose = 我方 win
      if (r.result === 'win') losses += Number(r.cnt);
      else wins += Number(r.cnt);
    }
    return { wins, losses };
  }
}
```

## 第七节 注意事项

1. **守方弟子不存在的兜底**：守方阵容是预设的，弟子可能后续被移除（目前版本没有遣散功能，但要兜底）。如果某弟子已不存在，该位置视为战力 0，名字显示"已离宗"。
2. **旧数据兼容**：旧 `sparring_log` 表不删，但新功能不再读写它。旧的切磋历史不会出现在新的演武录中。
3. **挑战结果消息**：格式类似 `"你的阵容 2:1 击败了 XXX！声望 +10，灵石 +100"` 或 `"你的阵容 0:2 不敌 XXX，挑战失败（无损失）"`。
4. **CSS 变量**：沿用现有的 --jade（胜/正面）、--red（负）、--muted（中性）、--surface（卡片背景）。
5. **Toast 通知**：挑战成功用 `emit('notify', 'success', '挑战胜利', message)`，失败用 `('warning', '挑战失败', message)`。
6. **守擂阵容不暴露给攻方**：公开档案只显示 `hasDefenseLineup: boolean`，不告诉攻方守方派了哪 3 个弟子——这是策略核心。
7. **单轮平局（战力完全相等，±15% 浮动后恰好一样）**：极低概率，算守方胜该轮（主场优势）。
