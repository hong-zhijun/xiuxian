# P5：玩家交易系统

3~5 人自用娱乐游戏。玩家之间可以互相送资源/交换资源。

**核心原则：简单直接。发起交易 → 对方接受/拒绝 → 资源转移。没有市场、没有手续费、没有锁定。**

---

## 一、数据库迁移 (migrations/0006_trades.sql)

```sql
CREATE TABLE trades (
  id TEXT PRIMARY KEY,
  from_sect_id TEXT NOT NULL REFERENCES sects(id),
  to_sect_id TEXT NOT NULL REFERENCES sects(id),
  offer TEXT NOT NULL DEFAULT '{}',
  request TEXT NOT NULL DEFAULT '{}',
  status TEXT NOT NULL DEFAULT 'pending',
  created_at INTEGER NOT NULL,
  resolved_at INTEGER
);

CREATE INDEX trades_to_sect_idx ON trades(to_sect_id, status);
CREATE INDEX trades_from_sect_idx ON trades(from_sect_id, created_at DESC);
```

字段说明：
- `offer`：发起方给出的资源，JSON 格式 `{"spiritStone": "50000", "herb": "20000"}`（最小单位）
- `request`：发起方想要的资源，同上格式。为空 `{}` 表示白送（赠送模式）
- `status`：`pending`（待处理）/ `accepted`（已完成）/ `rejected`（已拒绝）/ `cancelled`（已撤销）/ `expired`（已过期）

在 `apps/server/src/infra/db/readiness.ts` 的 REQUIRED_TABLES 里加上 `trades`。

## 二、后端交易模块 (apps/server/src/modules/game/trade.ts)

新建文件，实现交易逻辑。

### 2.1 发起交易

```
POST /game/trade/create
body: { toSectId: string, offer: Record<string, string>, request: Record<string, string> }
```

逻辑：
1. 查发起方宗门，先结算
2. 检查 offer 里的每种资源，发起方余额够不够。**不预扣**（简单起见，接受时再扣）
3. 检查 toSectId 存在且不是自己
4. 检查发起方没有超过 5 个 pending 交易（防刷屏）
5. 写入 trades 表，status = 'pending'
6. 交易 24 小时后自动视为过期（查询时判断，不用定时任务）
7. 返回交易 id

### 2.2 接受交易

```
POST /game/trade/accept
body: { tradeId: string }
```

逻辑：
1. 查交易记录，检查 status = 'pending' 且 to_sect_id = 当前用户的宗门 且未过期（created_at + 24h > now）
2. 结算双方宗门
3. 检查发起方的 offer 资源够不够（发起时没预扣，现在可能不够了）
4. 检查接受方的 request 资源够不够
5. 任一方资源不足 → 返回错误，不改状态（让发起方自己撤销或等过期）
6. 双方资源够 → 执行转移：发起方扣 offer 加 request，接受方扣 request 加 offer
7. 更新 status = 'accepted'，resolved_at = now
8. 用 D1 batch 一次性写入（两方的资源更新 + 交易状态更新）

### 2.3 拒绝交易

```
POST /game/trade/reject
body: { tradeId: string }
```

检查 status = 'pending' 且 to_sect_id = 当前用户。更新 status = 'rejected'。

### 2.4 撤销交易

```
POST /game/trade/cancel
body: { tradeId: string }
```

检查 status = 'pending' 且 from_sect_id = 当前用户。更新 status = 'cancelled'。

### 2.5 查看交易列表

```
GET /game/trades
```

返回当前用户相关的交易（发起的 + 收到的），最近 20 条，按 created_at DESC。查询时把超过 24 小时的 pending 标记为 expired（UPDATE 一次就行）。

### 2.6 查看所有宗门（用于选择交易对象）

```
GET /game/sects
```

返回所有宗门的 id + name + level（不含当前用户自己的）。就这几个人玩，直接全量返回。

### 4.1 API (修改 apps/web/src/api/game.ts)

加类型和函数：

```typescript
interface TradeView {
  id: string;
  fromSectId: string;
  fromSectName: string;
  toSectId: string;
  toSectName: string;
  offer: Record<string, string>;  // resourceId -> amount (最小单位)
  request: Record<string, string>;
  status: 'pending' | 'accepted' | 'rejected' | 'cancelled' | 'expired';
  createdAt: string;
  resolvedAt: string | null;
  isMine: boolean; // 是否是我发起的
}

interface SectListItem {
  id: string;
  name: string;
  level: number;
}

// API 函数
fetchSects(): Promise<SectListItem[]>
fetchTrades(): Promise<TradeView[]>
createTrade(toSectId, offer, request): Promise<{tradeId: string}>
acceptTrade(tradeId): Promise<void>
rejectTrade(tradeId): Promise<void>
cancelTrade(tradeId): Promise<void>
```

### 4.2 交易面板 (新建 apps/web/src/components/TradePanel.vue)

新建组件，在 SectScreen 的 `management-rail`（右栏，建筑面板下方）引入。沿用现有的面板风格：

```html
<section class="game-panel trade-panel">
  <header class="section-heading panel-heading compact-heading">
    <div>
      <p class="eyebrow">坊市往来</p>
      <h2>宗门互通</h2>
    </div>
    <span v-if="pendingCount > 0" class="count-badge">{{ pendingCount }} 待处理</span>
  </header>
  <!-- 内容 -->
</section>
```

**收到的交易**：列出 pending 且发给我的，每条用类似 `.building-card` 的紧凑行布局：
- 圆形图标显示对方宗名首字
- 「来自 XX宗」+ 给出/想要的资源
- 接受/拒绝用 `.action-button` 样式的小按钮

**我发起的交易**：pending 可撤销，已完成显示状态

**发起交易**：
- 选择目标宗门（用 `<select>` 或参考 AssignmentSelect 做自定义下拉）
- 资源输入用 `.field-control input` 样式，每种资源一个输入框（展示单位，留空=不给）
- 想要的资源同上，全留空=赠送模式
- 发起按钮用 `.action-button` + `.primary-action` 样式

数值输入用展示单位（玩家输入 50 灵石，前端转成 50000 最小单位发给后端）。

### 4.3 交易通知

交易操作结果用已有的 Toast 系统通知：`emit('notify', 'success', '交易完成', '...')`。
收到的 pending 交易数量 > 0 时，在面板标题显示 `count-badge`。

### 4.4 样式

在 `base.css` 里加 `.trade-panel`、`.trade-card`、`.trade-form` 等样式，配色和间距与现有的 `.building-panel` 保持一致。

### 4.5 交易操作后刷新

每次交易操作（发起/接受/拒绝/撤销）后，重新调用 `fetchTrades()` 刷新列表，同时调用 sync 刷新资源。
