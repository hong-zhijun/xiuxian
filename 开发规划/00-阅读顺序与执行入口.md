# 修仙宗门挂机游戏：开发规划与执行入口

版本 V1.1；2026-09-17；Cloudflare部署目标已明确，其他产品建议待确认；尚未开发代码。

## 1. 结论

**需要分期，建议 7 期，不能把基础需求中的“首版”作为一次性交付范围。**

原始需求同时包含离线经营、人物养成、剧情、战斗、社交、交易和全服活动。离线结算、交易与奖励正确性不能交给弱模型做页面时临时决定。

| 阶段 | 主题 | 交付用途 |
| --- | --- | --- |
| P0 | 工程、账号、安全与测试 | 可持续开发的基座 |
| P1 | 宗门经营与离线修炼 | 最小可玩版，仅内部试玩 |
| P2 | 功法、炼制、历练与战斗 | 成长闭环，定向封闭测试 |
| P3 | 弟子关系、人生、事件 | 内容体验检查点，小规模邀请测试 |
| P4 | 档案、拜访、切磋、榜单 | 轻量异步多人 |
| P5 | 玩家坊市 | 独立开关、限量灰度 |
| P6 | 世界妖兽、剩余建筑、上线加固 | 完整 V1.0，通过验收后开放 |

P1 不是完整基础需求的首版；P3 若单人经营仍不好玩，先调玩法，不继续堆多人系统。P6 才是本规划定义的完整 V1.0。

## 2. 仓库事实与缺口

- 根目录仅有 `基础需求.md`，没有代码、依赖、测试，当前也不是 Git 仓库。
- 原文第 11 节在挂机收益公式处结束，代码块未闭合；本轮保留原文不改。
- 账号、技术栈、数值、时间尺度、产销关系、部署和玩家规模均未定。
- 规划中的新增规则和数值是**建议基线**，不是已经确认的原始需求。
- 本轮只生成开发文档，不创建应用、不安装依赖、不启动服务器。

## 3. 阅读顺序

1. `01-产品范围与分期决策.md`：范围、延期与分期验收。
2. `02-技术架构与工程约定.md`：技术、目录、命令、安全。
3. `03-领域规则与数据契约.md`：数值、状态、结算、数据库。
4. `04-接口与页面契约.md`：接口、权限、页面和错误。
5. `05-测试验收与上线门禁.md`：完成标准及证据。
6. `06-弱模型执行说明与任务模板.md`：单任务执行规程。
7. `分期任务` 下 P0～P6：54 个任务卡。
8. `07-进度与决策记录.md`：进度、决策、交接。

已确认的新决策优先于旧规划；原始需求决定产品目标，领域规则决定实现语义；任务卡不能暗中改变领域规则。资产、安全、迁移规则不明确时记录问题，不静默猜测。

## 4. 直接交给弱模型

**每次只发一个任务 ID，不要让它“一次做完整个阶段”。**

首次提示词：

> 阅读基础需求，以及开发规划的 00、01、02、03、05、06 和 P0 文档。这次只执行 P0-01。核对前置条件后按任务卡创建文件，不实现后续任务。完成后运行对应检查，列出修改文件、命令与结果，并更新 07-进度与决策记录。不能运行的检查标为未执行，不能把待办写成通过。

后续使用 `06` 的模板。每期结束独立评审，通过后进入下一期；不允许先做全站空页面再补逻辑。

## 5. 投入与停止条件

- 54 项是验收单元，不代表 54 次模型回复；过大的任务继续拆成数据、服务、接口、页面和验证子任务。
- 完整 V1.0 粗估 70～120 人日，包含人工评审、调数值、验收，不是交付承诺。P1 后根据真实吞吐量重估。
- 默认不承诺多语言和商业化。
- 重复发奖、负资产、越权、存档不可恢复、旧浏览器白屏必须优先修复，停止新功能。

## 6. 五个待确认决策

1. 先交付 P1 试玩、再达完整 V1.0，默认接受。
2. 部署Cloudflare已明确；方案修订为 Vue + Pages（前端）+ Workers/Hono + D1（SQLite）（后端），本地Wrangler，不需要Docker。前后端分离部署，同域 Route 连接。
3. 离线收益上限 12 小时，真人 24 小时等于游戏 1 年，默认作为可调测试参数。
4. V1.0 不做自由留言、充值、强制日常、实时 PvP，默认接受。
5. 寿元死亡、渡劫死亡、叛离延期 V1.1，默认建议，但这是对原需求的明确延期，必须确认。

死亡在 P3 前、交易在 P5 前、上线规模在 P6 前确认。其他非阻塞决策不妨碍先做基座。
