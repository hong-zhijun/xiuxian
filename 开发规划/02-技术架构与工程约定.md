# 技术架构与工程约定

V1.2，2026-09-17：前后端拆为两个 Cloudflare 项目——前端 Cloudflare Pages、后端 Cloudflare Workers。**不需要 Docker，不需要安装 PostgreSQL，不使用 Fastify/Prisma。**

## 1. 固定技术路线

| 层次 | 选型 | 用途 |
| --- | --- | --- |
| 前端 | Vue 3、TypeScript、Vite、Vue Router、Pinia | 经营页面、人物、战报；保持原浏览器目标 |
| 前端托管 | Cloudflare Pages | 托管前端构建产物；自带CDN、分支预览部署 |
| 后端 | Cloudflare Workers + Hono | fetch API路由和业务服务，不是常驻Node服务器 |
| 数据库 | Cloudflare D1 | 基于SQLite；单服资产相关数据先放同一个D1数据库 |
| 数据访问 | D1 binding + 参数化SQL，SQL migrations | env.DB.prepare/bind/batch；先不引入ORM |
| 校验 | Zod | 请求、配置、事件DSL |
| 开发部署 | Wrangler、npm workspaces | 本地Workers/D1模拟、迁移、打包与部署 |
| 测试 | Vitest、Cloudflare Workers测试集成、Playwright | 纯逻辑、本地D1集成、页面回归；发布前staging D1验证 |
| 定时任务 | Cron Triggers + D1持久任务表 | 有界分批执行、租约、重试、幂等 |
| 日志 | Workers Observability、结构化console日志 | requestId、命令、失败任务；不得输出secret |

Node.js仅是本机npm/Vite/Wrangler的工具环境，不是线上应用服务器。P0-01核对当前工具支持版本并锁定，开发机为受支持现代系统；Win7仅为玩家浏览器兼容目标。

不把普通本地`.sqlite`文件上传到Workers作为持久数据库。Workers中使用D1 binding；本地使用同一绑定对应的Wrangler本地数据。不需要额外VPS。

### 前后端分离部署

前端（apps/web）部署为 Cloudflare Pages 项目，后端（apps/server）部署为 Cloudflare Workers 项目，是两个独立的 Cloudflare 项目。

**同域部署方案（推荐）**：将 Pages 和 Workers 绑定到同一个域名下，通过 Cloudflare Routes 将 `/api/*` 路由到 Workers，其余请求由 Pages 处理。这样无需 CORS 配置，Cookie 自然共享。例如：
- `game.example.com` → Pages（前端）
- `game.example.com/api/*` → Workers Route（后端）

**备选方案**：使用子域名（如 `api.game.example.com`），需要配置 CORS 和 Cookie domain。仅在同域路由不满足需求时使用。

Pages 优势：自带 CDN 缓存与自动失效、每次推送自动生成预览 URL、前后端独立部署互不影响。

V1先不引入R2、KV、Queues、Durable Objects或Hyperdrive。静态图放assets；游戏资产只进D1；新增平台组件须有实际瓶颈与确认决策，不由弱模型自由扩展。


apps/server 是 Worker，不创建 listen 端口、不建 main.ts 或常驻 worker.ts。index.ts 将 fetch 交给 Hono，将 scheduled 交给持久任务执行器。apps/web 是纯前端 SPA，构建产物部署到 Pages。

routes/schema/service/repository按业务分层。service计算命令计划，repository组装参数化SQL；不从route直接拼SQL。前端不引用数据库模型，game-core不依赖框架、真实时钟或Cloudflare绑定。

## 3. D1一致性：必须在P0先验证

D1 `batch()`支持一组SQL语句整体成功或整体回滚；**它不是允许在JavaScript里读数据、await、再任意写入的交互式事务**。不能搬用PostgreSQL的SELECT FOR UPDATE、连接池、BEGIN/COMMIT或Prisma交互事务。

统一命令流程：

1. 解析输入、鉴权、归属检查；同key查已提交CommandReceipt，摘要不同拒绝。
2. 从主库读取完整业务依赖快照；v1不启用只读副本。用一致的读批次或对象stateVersion校验读取，不拼接不同版本余额与弟子。
3. 固定本次serverNow/随机种子，用纯函数计算旧状态结算与命令结果；只构造计划，不先写余额。
4. 组装**一次**D1 batch：校验全部预期版本与业务条件、更新全部资产和状态、增加版本、写流水/奖励/幂等响应。
5. batch失败则整体回滚。版本冲突重新读与计算，最多3次；命中同key已提交结果则返回该结果。仍冲突返回STATE_CONFLICT，不无限自旋。

所有影响宗门子表的写入都必须校验并增加Sect.stateVersion。共享MarketOrder/BossInstance/RewardMail/限次记录也有版本或等效唯一状态条件。买卖同时验证两个宗门和订单，在同一个D1库、同一个batch提交；跨数据库没有这一原子保证，所以V1不按玩家拆库。

### 防止“零行更新却继续发奖”

仅使用 `UPDATE ... WHERE version=?` 不够：更新0行通常不是SQL错误，后续发货可能仍执行。**禁止batch完成后才发现0行，再尝试事后补偿原子性。**

建议P0-05实现极小的数据库断言机制：MutationGuard(commandId TEXT PRIMARY KEY, valid INTEGER NOT NULL CHECK(valid=1))。批次第一条插入1或0，值来自SQL EXISTS/COUNT谓词，一次检查所有预期版本、归属、余额、订单状态等；任何条件不符插0触发约束错误，整批回滚。之后才执行已断言的业务更新、CommandReceipt唯一写入，最后删除Guard记录。所有SQL在同一batch，不能拆成网络往返。

- Guard仅为技术断言，不含复杂业务脚本；SQL全部参数化；空/NULL条件必须显式转为0。
- 命令唯一键、任务来源唯一键、CHECK约束是最后一道防线，不用ON CONFLICT DO NOTHING吞掉重复命令后继续扣款。
- P0必须用本地D1证明断言失败、后续SQL失败、重复键失败均整体回滚；P5上线前用staging远程D1重复验证。
- 生产测试随机源仅由服务端生成。冲突重算沿用同一请求内部种子，客户端不能指定；已提交结果永远重放不重掷。
- 截止时间使用本次服务端请求/调度捕获的时间，冲突重试刷新时间；必要时在断言SQL检查数据库当前时间尚未过期。前端时钟无裁决权。
- 捕获D1异常后区分已提交重放、版本冲突、业务不满足、未知故障；对外不暴露SQL。不能把所有约束失败都当成功或无限重试。

这套基础必须由P0-05单独实现并评审；后续弱模型只使用command-plan/batch封装，不每个模块重新设计事务。

## 4. D1类型和任务约定

时间用INTEGER毫秒、API用UTC ISO字符串；布尔存0/1；结构化快照存校验过的JSON TEXT；外键、CHECK、UNIQUE用SQL migrations定义。

D1 JS绑定目前不能直接bind BigInt。资源仍按1单位=1000最小单位、API十进制字符串；存入D1前转安全整数，单值绝对上限建议1,000,000,000,000,000且不超过Number.MAX_SAFE_INTEGER。乘法/比例/累计在纯函数内用BigInt，再检查范围后转number绑定。不能让SQLite溢出整数后静默转换REAL。

Cron只做有界批次扫描到期任务：查询索引、条件领取lease、执行可幂等命令、保存游标；失败下次继续，不常驻while循环。请求sync也可推进本人到期任务，二者以版本/来源唯一约束协调。waitUntil不是持久队列，也不能保证未落库任务执行。

榜单/Boss分批发奖，每小批一个可恢复命令；无超长事务。数据库限额、语句大小、单次查询/CPU预算由P0和P6核对当期官方限制，不能承诺整个游戏永远免费。

## 5. 账号与安全

- 账号密码+不透明服务端session；保留原体验，但不使用依赖Node原生二进制的密码库。
- P0-04选用成熟、Workers兼容的密码哈希实现（优先评估Argon2id WASM，或Web Crypto PBKDF2安全方案）；具体库/参数必须形成决策并验证Workers CPU/内存限制，不手写哈希、不为免费额度擅自降安全强度。此项未验证不得开放注册。
- session随机token由Web Crypto生成；D1仅存摘要与期限；Cookie HttpOnly/SameSite=Lax/生产Secure；退出失效。
- 所有写请求验Origin；登录/注册只允许同源JSON并限频；已登录写请求含退出再验CSRF。
- 初期邀请内测，REGISTRATION_ENABLED默认false。安全限频不能依赖全局内存Map；使用原子D1计数或经核验的平台能力。
- .dev.vars仅本地secret；远程用Wrangler secrets；不打印、不提交token。环境只给最小权限。
- API私有响应禁止公共缓存；未知/api路由返回JSON 404，不能落入SPA的index.html。

## 6. 配置与本地运行

apps/server 的 wrangler.jsonc 设置 main、DB binding、cron、observability、routes（生产环境将 `/api/*` 路由到此 Worker）；新项目 compatibility_date 按实施当天设置，所需 nodejs_compat 按依赖核验。`wrangler types` 生成绑定类型，不能手写长期漂移的 Env。

apps/web 是标准 Vite + Vue 项目，通过 `wrangler pages deploy` 或 Git 集成部署到 Pages。

开发时 Vite dev server 代理 `/api/*` 到 Wrangler 本地 Worker；构建预览分别运行 Worker 本地服务和 Vite preview。开发/自动测试/staging/production 分别使用独立数据，默认不得 remote:true 连接生产。

```text
npm ci
npm run dev                    # Vite dev server + Wrangler本地Worker/D1并行启动
npm run build                  # 分别构建web和server
npm run typecheck
npm run lint
npm run test:unit
npm run test:integration        # 本地workerd/D1，不是mock
npm run test:e2e
npm run db:migrate:local        # 包装wrangler d1 migrations apply ... --local
npm run db:seed:local
npm run cf:types               # 包装wrangler types（apps/server）
npm run deploy:server:dry-run  # wrangler deploy --dry-run（Worker）
npm run deploy:web:dry-run     # wrangler pages deploy --dry-run 或构建验证（Pages）
```

以上脚本P0创建并实际验证。远程迁移/创建资源/部署有独立命令和明确环境，必须经用户授权；不在postinstall或测试脚本里隐式创建云资源。

不要求DATABASE_URL、TEST_DATABASE_URL或数据库账号密码；环境通过DB绑定和隔离状态目录选择。测试使用独立本地持久化目录/隔离测试存储，清理前验证路径；远程集成测试仅对明确staging数据库执行。

## 7. 界面兼容与发布

前端仍显式build.target=['chrome109','firefox115']，JS语法编译不等于Web API/CSS兼容；真正旧浏览器实测是发布门禁。页面仍是经营工具而非营销首页，保留原设计与无障碍要求。

Cloudflare 部署前验证：Pages SPA 刷新正常、Workers Route `/api/*` 优先级正确、同域 Cookie/CSRF、D1 binding 与 Secrets、Cron、迁移、可观测性和故障开关。确认 Pages 自定义域名与 Workers Route 不冲突。D1备份采用Time Travel加按需导出，确认当前套餐保留窗口；在staging演练恢复，不自行管理WAL。恢复数据库前需停止写入和调度，评估回档后的跨系统影响。
