# 领域规则与数据契约

本文件是弱模型实现的规则基线。参数可调；时间、幂等、资产守恒和权限不允许随意变化。

V1.2平台约定：使用Cloudflare Workers + D1（SQLite），前端由 Pages 托管。本文件的”事务”均指02文档的版本断言与单次D1 batch，不是交互式SQL事务或行锁；所有相关资产在同一D1库中。

## 1. 单位、时钟、标识

- ID：UUID 字符串；所有业务数据带 serverId 或可经 Sect 唯一追溯 serverId。
- 日期：D1 INTEGER存UTC整数毫秒；API UTC ISO 8601。
- 自然日/周以 UTC+8 划分，不取用户时区；周一 00:00 开新周期；前端显示结算时区。
- 资源存非负SQLite INTEGER最小单位，1展示单位=1000最小单位；API十进制字符串。D1绑定用安全整数number，不直接绑定BigInt；纯计算用BigInt，落库前检查02定义的安全上限。
- 修为、经验、伤害、数量为非负整数；概率用 0～10000 基点；乘除用整数规则、明确舍入，金额不使用浮点数。
- 前端允许格式化，不能拿格式化后的数字参与交易或保存。
- 所有变化可追溯 commandId/sourceId；业务时间由服务端取，不信任客户端时间。

## 3. 离线结算精确定义

定义 L=最后结算时间、N=事务服务器时间、C=12 小时离线经济上限。

```text
elapsed = max(0, N - L)
economicEnd = L + min(elapsed, C)
经济生产与修炼只累计 [L, economicEnd]
真实世界任务/冷却/伤势到期可推进到 N
lastSettledAt = max(L, N)
```

选择“离线最早 12 小时”计收益，不是最后 12 小时。超过上限的时段永久丢弃，不能下次刷新补领。

若 N < L，收益为 0 且不回拨 lastSettledAt；记录时钟告警。客户端改时钟不影响 N。

P1 单段公式，产量先统一成每小时最小单位整数：

```text
numerator = ratePerHour * durationMs + remainder
gain = floor(numerator / 3600000)
remainder = numerator % 3600000
accepted = min(gain, capacity - balance)
overflow = gain - accepted
```

资源触顶时丢弃溢出及该资源小数余量，避免满仓暗存收益；修炼到突破门槛时同样停止积累并清理余量。不自动突破，不自动花丹药。

修为每名修炼弟子单独记余量；挂机修炼不持续扣灵气，灵气用于突破/研究，避免额外“耗尽时刻”分段。以后要改成持续消耗须先补边界算法。

所有改变产量/状态的操作先结算旧状态，包括派工、升级、装备、功法、关系修正、事件效果。事务中只结算一次，再执行命令。

### P2 起的时间边界

按时间升序分段，边界包括 economicEnd、伤势恢复、历练结束、炼制完成、限时效果到期、N。同一毫秒按“到期状态 → 完成任务 → 自动事件候选”顺序，用稳定 ID 再排序。

- 只在与 [L,economicEnd] 相交的片段产生经济收益。
- 伤势到期：恢复指定岗位；历练结束：弟子恢复出发前岗位（岗位不可用则 idle），奖励转 ready 等待领取。
- 炼制结束：产物转 ready，不自动开下一单；炼制管理员与修炼互斥，无自动连产。
- 队列/远征在离线超过 12 小时后仍可完成，但超过上限的时间不再生产。
- 无生产影响的订单/Boss不在宗门结算里推进，由scheduled处理独立持久任务；同步与调度共用幂等完成服务。
- 最多 1 个炼丹、1 个炼器队列、1 个研究队列、2 个远征；事件候选最多每宗门 5 个，防止无限补事件。
- 时间推进只生成结果或待领取记录；不自动消费稀有资源，不自动执行不可逆人生选择。

**验算例**：20 药材/小时，离线 2.5 小时得 50；离线 30 小时最多得 240，立即再次请求为 0。弟子前 2 小时在历练、随后回采矿，离线 5 小时只采矿 3 小时；离线 30 小时只采矿上限内的 10 小时。

## 4. 弟子、岗位、修炼与突破

岗位枚举：idle、cultivating、herbGathering、oreGathering、buildingManager、expedition。伤势为独立 injuredUntil，不混进岗位枚举；远征关联 expeditionId；同一弟子同时只占一个岗位。

基础字段包括性别展示、入门年龄、寿元、灵根、资质 1～100、天赋、性格；性别不作为属性强弱修正。

境界配置使用 realmId/stage/requiredCultivation；建议每大境界 3 小阶段，不直接用中文比较顺序。

```text
每小时基础修为 = 60
资质系数 = 8000 + aptitude * 40            # 基点，范围 0.8～1.2
最终速率 = floor(基础修为 * 各已归一化系数 / 对应基点分母)
```

先相加同类加成，再乘不同类型，总成长加成封顶由配置指定；显示最终速率及来源。P1 炼气三阶段门槛建议 30/90/180；初始修为 0，调速须重新验证首日节奏。

突破命令必须达到门槛、无伤势/冷却、非远征；服务端扣足全部成本后抽一次随机。概率 = clamp(基础 + 丹药 + 聚灵阵 + 师父 + 天赋/装备，500，9500)。P1 默认基础 8000，仅阵法和已实现天赋可加成。

成功：进入下一阶段，修为清零，记录史册。失败：保留门槛的 90% 修为，冷却 5 分钟，不永久死亡；若配置伤势则显示持续时间。重试同幂等键不能重新掷骰。

招募：每日 3 次、每次 50 灵石；每次直接生成 1 人，无付费刷新池；满员不扣费不耗次数。候选预览/挑选留待后续，避免无限刷资质。

## 5. 物品、制作与功法

- 基础资源在 ResourceBalance；丹药/残页/灵兽材料在 ItemStack；法器等独立物件在 ItemInstance。药材/矿石交易由统一资产适配层扣 ResourceBalance，不能在两张表同时存在可花余额。
- ItemStack 唯一键为 sectId、itemDefId、binding；Instance 有 ownerSectId、binding、location、词条、configVersion。
- location 至少 inventory/equipped/escrow/mail；同物品只能在一个位置。
- 队列开始时一次扣材料，保存配方版本/产物/完成时间；到期产物进入 ready，领取一次。队列不允许取消，提交前明确告知。
- 相同模板物品消费默认先绑定后未绑定，明细写流水；任一绑定材料参与炼制则产物绑定，禁止洗掉绑定。突破丹请求只给 pillItemDefId，服务端固定消耗1份；不混用实例ID与模板ID。
- ready 奖励未领取不占背包，可一直保留；容量不足拒绝整次领取，不部分发货；可堆叠数量仍有安全上限。
- 除挂机生产外不静默丢奖励：事件/任务等资源奖励容量不足时整份转唯一邮件，页面说明；需领取的整包奖励配置必须可被目标阶段可达容量容纳，避免永远领不出。
- 功法先研究至宗门已解锁，再向弟子传承；主修 1、辅助 1，同一本不能同时占两槽；升级/换装先结算。
- 第一批功法残页来自历练，不从商城凭空出现；炼丹榜只计制作完成的合格数量，不计领取或转手。

## 6. 自动战斗

每队 1～5 名不同弟子，前排最多 3，后排最多 2；保存阵容只是引用，开始战斗才制作完整数值快照。快照包含 configVersion、规则版本、属性、技能、装备、站位、策略；不可含库存秘密信息。

V1.0 基础属性：HP、攻击、防御、速度、暴击率、暴击倍率。回合按速度降序，平速按固定槽位与队伍序排序；每回合每存活单位一次行动；最多 50 回合。

普通目标先前排，再后排；基础伤害 max(1, 攻击-防御)，暴击按基点计算并向下取整；防御减伤不产生负伤害。三策略采用配置：均衡无修正、强攻攻击 +10% 防御 -10%、固守防御 +10% 攻击 -10%。

技能首批仅 directDamage/heal/buff 三种白名单效果，无脚本、无无限反击或召唤；最多每人 2 个主动效果。P2-04 固定触发时机、持续回合与叠加规则后再写引擎。

50 回合未结束判平局；PvE 平局按失败，PvP 不给胜利积分，Boss 取已造成伤害。一次战斗持久化快照、种子、事件序列、结果；重播读日志，不重算随机。

## 7. 人物与事件

- 游戏年龄：入门年龄 + floor((N-ageAnchor)/24小时)，不受 12 小时经济上限影响；只在 P3 开启。
- V1.0 到寿元只给长寿提醒，不自动死亡；隐退必须本人确认，至少保留 1 名活跃弟子，不得隐退正在远征/装备托管中的弟子。
- 关系：师徒有方向；好友/道侣/仇敌/竞争/家族使用小 ID 在前的无向边；每类型每对唯一，不允许自关系。
- 一人最多 1 名师父、1 名道侣；拜师无环；道侣双方均须游戏年龄 >=18；仇敌与好友/道侣互斥；同门竞争可与好友并存。
- DSL 条件白名单：资源、境界、年龄、岗位、关系、前置事件；效果白名单：资源、修为、关系、声望、伤势、后续事件。禁止 eval/任意 JavaScript/SQL。
- 事件 pending→resolved/expired，选择时重验条件；随机一次；唯一 eventInstanceId 保障不重复奖励。
- 随机日常事件按UTC+8每4小时一个固定窗口，每窗口最多判定一次；持久化宗门+窗口唯一记录，没触发也记录。离线最多补经济有效区间内的3个窗口，受5条待办上限约束；被跳过窗口不积攒到下次刷新。任务/关系产生的显式事件另用sourceId去重，不占随机抽取机会。
- 默认事件 24 小时过期，过期不扣资产、不自动选危险选项；后续事件最多 3 跳，循环配置拒绝导入；事件冷却以宗门+模板计。
- 暂定性格只做小幅效果，每项 <=5%，不隐藏改变突破成功率；界面展示来源。

## 8. 异步多人规则

- 切磋每天 5 次，同目标最多 1 次/日；不能打自己、跨服或封禁目标；无有效防守快照则不可挑战。
- 防守快照由玩家显式保存；升级装备不自动改旧快照，页面提醒；旧配置快照需保留兼容解释器或标为失效要求重存。
- 切磋胜 +10 声望、负/平 +0；不改变防守方声望/库存/伤势；双方可看同一战报。
- 拜访本人禁止；固定礼物每日总计 3 次、每目标 1 次，花 5 灵石、对方获得 1 点友好记录，不收资源，避免绕坊市转账。
- 论道/公开功法参悟每宗门每日各 1 次，只给小量本宗弟子修为，需有符合条件的代表弟子/公开功法；跨宗门事件不消耗对方私有资源。
- 排行周期快照固定结束时间；P4 使用“已提交状态”分数，不为每次浏览自动结算所有宗门；公开更新时间与指标定义。
- 综合分 = 活跃弟子战力总和 + 宗门等级×100 + 建筑等级和×20；战力公式配置化且不等于战斗结果；声望榜按本周期新增声望；炼丹榜按本周期完成数；弟子榜按快照战力。
- 同分按达到分数时间较早优先，再按 ID 排序；奖励经 RewardMail，unique(periodId,boardType,sectId)，无重复结算。

## 9. 坊市规则

- 单服、只用灵石、固定价、整单购买；绑定/装备中/任务占用物品不可上架；不卖充值币。
- 每单 1～99 件；法器仅 1 件；有效期 24 小时；每宗门最多 10 个在售单，每天最多新挂 20 单、买 20 单；撤单不返每日挂单次数。
- 配置给每 itemDef 独立 minPrice/maxPrice，整数展示灵石；手续费为总价的 5%，向上取整到最小单位。
- API unitPrice/totalPrice 都是最小单位十进制字符串，unitPrice须为1000倍数；quantity是整数件数，基础药材/矿石每件对应1000最小资源单位。后端显式转换，不把展示单位直接入账。
- 挂牌时净收入不得超过卖方当前灵石总容量（不是可用空位）；已挂订单因此能通过腾出空间领取整笔收入，不能制造永远超过仓库容量的应收邮件。V1.0 不降低已有仓库容量。
- 挂牌即时把商品从可用资产移入托管；不能只存数量仍留库存。
- 买单读取订单与双方宗门快照，按02使用batch首条SQL断言版本/归属/到期/余额/容量/限额/非本人；扣买方总价、卖方收入总价-税、发货、订单sold、流水、幂等响应在同一batch提交；断言失败整体回滚。
- 灵石守恒：买方减少 = 卖方增加 + 税；物品守恒：卖方可用减少 = 托管增加，成交时托管减少 = 买方增加。
- 卖方灵石满仓时，收入进入持久 RewardMail，不截断；买方接收不下则整单失败。自动生产才允许丢溢出，交易资产不能丢。
- 撤单/过期返回物品至唯一 RewardMail，避免仓库容量变化导致丢物；sold/cancelled/expired 为终态。
- 到期由数据库 expiresAt 判定，worker 晚运行也不能买过期单；双买、买与撤单、买与过期必须最多一个成功。

## 10. 世界妖兽规则

单服每 24 小时一场、活动 12 小时，每宗门每日最多 3 次。实例 scheduled→active→killed/expired→rewarded；过期奖励与击杀奖励分配置。

服务端固定队伍与Boss快照算战斗，在同一D1 batch断言Boss/宗门版本及活动状态。实际贡献=min(原始伤害,快照剩余HP)，HP不小于0；版本变动重读重算，已结束拒绝且不耗次数。

战斗在提交batch前计算，绑定输入hash/状态版本；断言发现己方阵容或Boss变化须重算或返回冲突，不能拿过期结果扣次数。不能依赖Worker实例内存互斥。

累计贡献不超过初始HP；同幂等键只记一次攻击。击杀与截止竞态由服务端时间、版本断言和唯一状态转换确定唯一终态。scheduled按稳定贡献分批生成奖励邮件，唯一bossId+sectId+rewardType，失败可续跑。

资源非负、金额安全上限、状态合法使用D1 CHECK/UNIQUE/外键；结构化快照用已校验JSON TEXT；迁移使用D1兼容SQL。Sect子表统一受父stateVersion断言保护，订单/Boss/邮件也须版本或唯一状态断言；跨字段岗位限制由原子batch与集成测试守护。逻辑删除不能绕过任务/交易引用。

## 12. 配置版本与审计

配置按内容哈希/版本发布，启动校验引用、概率、成本、循环、溢出。战斗、配方、远征持久化实际版本和必要快照。

V1.0 暂不在线热更新影响挂机产量的配置。默认一次存档生命周期固定经济 configVersion，升级配置需维护窗口、先用旧版本结算到切换时间、再迁移指针；不能新费率追溯整段离线。

P1 起流水记录结算区间/接受量/溢出量、命令成本和奖励；P2 后 RewardMail 与业务来源唯一；幂等记录可清理，但订单、事件、队列、Boss 奖励的业务唯一约束不得因清理消失。

RewardMail 的 sourceId 必须确定性命名：排行榜为 periodId:boardType，妖兽为 bossId:rewardType，订单为 orderId:return 或 orderId:proceeds；与 sourceType、sectId 组成唯一键，不能每次重试生成随机sourceId。
